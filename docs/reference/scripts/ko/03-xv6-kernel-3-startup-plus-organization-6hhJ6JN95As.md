## 한국어 번역

이 비디오는 xv6 운영체제 커널에 대한 시리즈의 일부입니다. 이 비디오에서는 main 함수(메인 함수)를 소개하고, 부팅(시작) 절차에 대해 간단히 이야기하겠습니다. 그 전에
파일 구성에 대해서 먼저 살펴보고, 마지막에는 금방 처리할 수 있는 몇 개의 작은 파일들을 훑어보며 마무리하겠습니다. 우선 xv6 시스템에 포함된 파일들부터 시작해 봅시다.

여기에 xv6에 포함된 모든 파일들을 나열해 두었습니다. 보시는 것처럼 그리 많지 않습니다. 구성은 꽤 단순한 편입니다. kernel과 user 두 개의 디렉터리가 있고, 이쪽은
kernel 디렉터리에 들어 있는 파일들입니다. 기본적으로 C 코드 파일들이 여러 개 있고, 헤더 파일들도 몇 개 있습니다. 어셈블리 언어 파일도 몇 개 있는데, entry.s가
있고 이 파일에 대해서는 곧 설명하겠습니다.

그 밖에 kernelvec, switch.s(꽤 흥미로운 파일입니다), trampoline.s 같은 파일이 있고, initcode.s도 있습니다. 또 링커가 사용하는 파일도 하나
있습니다. user 디렉터리에는 초기 프로세스의 코드와 사용자 애플리케이션 프로그램들, 즉 셸과 cat, echo 같은 사용자 모드 프로그램들의 코드가 들어 있습니다. 그리고 이들
파일을 빌드하기 위한 Makefile이 하나 있고, README와 LICENSE 파일도 있습니다. 전반적으로 꽤 단순한 구성입니다.

xv6 시스템은 멀티코어 컴퓨터에서 실행되며, 부팅이 시작될 때 각 코어는 동시에 실행을 시작합니다. 모두 같은 시점에 시작합니다. 공유 메모리 시스템이기 때문에 모든 코어는
정확히 같은 메모리를 공유하고, 모두 똑같은 코드를 실행하기 시작합니다. 그 코드는 entry.s라는 파일 안에 들어 있습니다. 이 파일은 그리 길지 않고 몇 줄 되지 않습니다.
이 코드가 실행된 다음에는 start.c 파일 안에 있는 start라는 C 함수로 제어를 넘기고, 그런 다음 main 함수로 제어를 넘기게 됩니다. entry 파일에 들어 있는
어셈블리 코드는 기본적으로 C 프로그램을 실행할 수 있도록 환경을 준비하는 일을 합니다.

구체적으로는 스택 포인터 레지스터, 즉 sp 레지스터를 초기화하고 tp 레지스터도 초기화합니다. 각 코어는 메인 메모리를 공유하므로 같은 전역 변수 집합에 접근하게 됩니다. 하지만
각 코어는 자신만의 스택이 필요하고, 스택이 서로 겹치면 전혀 동작하지 않습니다. 따라서 각 코어마다 별도의 스택 공간이 있고, entry.s 안의 코드는 해당 코어에 알맞게 스택
포인터 레지스터를 초기화합니다.

또 tp 레지스터가 있는데, 이름은 thread pointer의 약자이지만 실제로는 코어 번호를 담습니다. 즉 0, 1, 2 … 이런 식의 코어 번호가 들어가고, 어떤 스레드
포인터 같은 것이 들어가는 것은 아닙니다. 이 레지스터 값은 해당 코어에서는 계속 일정하게 유지됩니다. 그래서 코드가 언제든지 “지금 나는 어느 코어에서 실행 중인가?”를 물어볼
수 있게 해 줍니다. 이런 것들이 설정된 다음에야 start 함수로 제어를 넘깁니다.

다른 비디오에서 RISC-V 프로세서가 실행할 수 있는 여러 모드에 대해 이야기한 적이 있습니다. machine 모드, supervisor 모드, user 모드가 있고, 커널
전체는 start.c에 들어 있는 아주 작은 일부 코드를 제외하면 전부 supervisor 모드에서 실행됩니다. 시스템이 처음 실행을 시작할 때는 machine 모드에서 실행을
시작하고,

여기 있는 코드가 몇 가지 자잘한 작업을 처리한 다음 supervisor 모드로 전환합니다. 이후에는 코어들이 supervisor 모드에 머무르게 됩니다. 이제 main 함수로
넘어가 보겠습니다. 여기 main.c의 코드가 있는데, 길지 않고 main 함수 하나만 들어 있습니다. 어떻게 동작하는지 보죠. 각 코어는 이 코드를 병렬로 실행하기 시작한다는
점을 기억해야 합니다. 그러니

모든 코어가 이 if 문부터 시작합니다. cpuid는 짧은 함수인데, 기본적으로 tp 레지스터 값을 읽어서 반환합니다. 따라서 코어 0에서는 이 함수가 0을 반환하고, 코어 0은
여기 있는 코드를 실행합니다. 나머지 모든 코어는 대신 이쪽 코드를 실행합니다. 코드가 무슨 일을 하는지 살펴보면, 코어 0은 초기화를 담당합니다. 그래서 init 무언가,
init 이것저것 하는 함수 호출이 많이 보입니다. 또 “kernel is booting”이라는 메시지도 출력합니다. 여기에 전역 변수, 또는 공유 변수가 하나 있는데, 메모리
공간에 있으므로 당연히 모든 코어가 접근할 수 있고, 동기화를 위해 사용됩니다. 여기 있는 volatile이라는 키워드는 약간의 C 매직 같은 것으로, 이 변수가 여러 코어나 동시
실행되는 스레드에 의해 동기화 용도로 사용된다는 뜻입니다.

실제로 이 변수는 다른 코어들의 시작 시점을 제어하는 데 사용됩니다. 이 변수는 처음에 0, 즉 false라고 생각할 수 있는 값으로 초기화되고, 코어 0이 초기화를 모두 끝내면
true로 바꿉니다. 다른 모든 코어는 이 값을 검사하는 바쁜 대기 루프에 들어가서, 이 값이 true가 될 때까지 계속 검사합니다.

true가 되는 순간 이쪽 코드를 실행합니다. 가장 먼저 “hart something is starting” 같은 메시지를 출력합니다. 여기서 hart라는 용어는 이 비디오들에서는
코어와 동의어로 쓰입니다. 그러니까 “core 1 is starting”, “core 2 is starting” 이런 식으로 찍는 것이고, 여기에서 자기 자신의 core 또는
CPU id를 읽어오고 있습니다. 코어 0이 마지막으로 하는 일은 init 프로세스의 코드를 시작하는 것입니다. 그게 여기에서 일어나고, 그 다음에 started를 1로
설정합니다. 그리고 다른 코어들은 여기에서 kmeminit, trapinit, xinit 같은 초기화를 수행합니다. 이것들은 코어별 초기화 작업이고, 코어 0에서도 역시
수행됩니다. kvm, trapinit, xinit 같은 것들이 코어 0에서는 위쪽에서 수행됩니다. 이렇게 모든 코어에서 이런 작업이 끝나면,

각 코어는 scheduler 함수를 호출합니다. scheduler가 하는 일은 실행할 프로세스를 찾는 것입니다. 그 시점부터 모든 코어가 프로세스들을 실행하기 시작합니다. 여기
sync라는 함수도 보이는데, 이것도 역시 약간의 컴파일러 매직입니다. 컴파일러는 최적화를 시도하는데, 이 함수는 컴파일러에게 “좀 진정해라”라며 그런 최적화를 하지 말라고
알려줍니다.

컴파일러는 더 나은 성능과 효율을 위해 코드의 실행 순서를 재배치할 수 있습니다. synchronize가 하는 일은 컴파일러에게 “위에 있는 것들을 전부 다 끝내고 나서, 그
다음에 아래에 있는 것들을 시작하라”고 알려주는 것입니다. 다시 말해, “이 초기화들을 전부 마치기 전에 이 변수를 1로 바꾸지 말라”고 요구하는 겁니다. 여기서 컴파일러에게
“내가 무엇을 하고 있는지 네가 다 이해 못할 수도 있지만, 어쨌든 위에 있는 것들을 전부 끝내기 전에는 저 변수를 1로 바꾸려고 생각도 하지 말라”고 말해 주는 셈입니다.
마찬가지로 아래쪽에서는 컴파일러에게 “이 while 루프를 끝내기 전에는 이 아래쪽 코드를 실행하지 말라”고 알려줍니다. 자, 이제 간단히 살펴보고 넘어가고 싶은 작은 파일 몇
개가 있습니다.

먼저 types.h인데, 여기에는 이 typedef 들만 들어 있습니다. 아마 이런 축약형 타입 이름들은 이미 익숙할 것입니다. 우리가 사용하는 아키텍처는 RISC-V
아키텍처이고, 툴체인은 64비트 머신을 대상으로 합니다. 정수는 32비트가 되고, 그래서 부호 없는 8비트 값, 부호 없는 16비트 값, 부호 없는 32비트 값을 이렇게
정의합니다.

unsigned 64-bit 값에 대해서는 주소와 포인터에 꽤 자주 이 uint64 타입을 사용합니다.

자, 다음으로 보고 싶은 파일은 param.h 입니다. 커널 안에는 하드코딩되어 있는 것들이 여러 개 있는데, 이것들을 빠르게 살펴보겠습니다.

먼저 proc에서, 최대 프로세스 개수는 그냥 64로 정해져 있습니다. 코어 개수는 8개로 되어 있고요. 그다음에 다른 것들, 열린 파일의 개수, 시스템 전체에서 동시에 열 수
있는 파일 개수, inode 개수, 디바이스 개수, 루트 디바이스 번호 rootdev, max argument, 이는 exec 시스템 콜에서 가질 수 있는 인자의 최대 개수입니다.
max op blocks, log size, nbuf, fssize, maxpath, maxpath는 파일 경로 이름에서 가질 수 있는 최대 문자 수입니다.

마지막으로 desk.h라는 파일을 보고 싶습니다. 이 파일은 이 네 페이지에 걸쳐 나와 있어서 무슨 일이 일어나는지 볼 수 있는데, 기본적으로 컴파일러를 위한 것이고 함수
프로토타입들이 잔뜩 들어 있습니다.

예를 들어, console.c 파일에는 적어도 여기 나와 있는 이 세 개의 함수들이 들어 있고, 이 함수들은 다른 파일들에서도 사용될 수 있습니다. 그래서 이 파일은 기본적으로
함수 프로토타입 모음일 뿐이고, 특별히 흥미로운 내용은 없습니다. 이 파일들 전부는 나중에 다시 만나게 될 겁니다.

이제 이 모든 페이지를 훑어봤고, 마지막 페이지에는 전처리기 매크로가 하나 있습니다. 아마 다른 곳에서 본 적이 있을 텐데, 배열 원소의 개수를 구하는 매크로입니다. 여기에는 어떤
변수, 배열 변수 이름이 들어가고, 이 매크로가 하는 일은 “전체 배열의 크기가 얼마인가?” 그리고 “단일 원소 하나의 크기가 얼마인가?”를 묻고, 그 둘을 나눠서 원소 개수를
돌려주는 것입니다.
