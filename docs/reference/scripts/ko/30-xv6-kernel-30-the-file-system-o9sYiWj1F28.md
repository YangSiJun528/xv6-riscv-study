## 한국어 번역

이 비디오는 xv6 운영체제 커널에 대한 동영상 강좌의 일부입니다. 파일 시스템과 관련된 코드가 상당히 많기 때문에, 저는 이것을 여러 개의 다른 비디오로 나누었습니다. 지금까지는
버퍼 캐시 시스템과 디스크 로깅 시스템에 대해 이미 이야기했습니다. 앞으로의 비디오에서는 코드 자체를 다룰 예정이지만, 이 비디오에서는 파일 시스템이 디스크 위에 어떻게 표현되어
있는지에 초점을 맞추려고 합니다.

그래서 이번 비디오에서는 디렉터리와 파일을 위한 디스크 조직 방식과 레이아웃에 대해 이야기하겠습니다. 이전에 로깅 시스템을 이야기할 때, 디스크의 개략적인 그림을 보여준 적이
있습니다. 여기서 각각의 작은 사각형이 디스크 상의 하나의 블록을 나타냈고, 로그 영역과 메인 블록 영역 등을 포함한 여러 내용이 있었습니다. 이제 그 그림을 조금 단순화해서,
디스크 블록 영역만 보겠습니다.

즉, 디스크 위에 순차적으로 배열된 디스크 블록들의 집합만 있다고 생각하겠습니다. 우리가 이미 살펴본 코드에는 이 블록들에 접근할 수 있게 해 주는 여러 함수들이 제공됩니다.
여기에는 디스크 상의 블록에 접근하는 코드가 어떤 모습일지 예시로 나와 있습니다. 특히 bread라는 함수가 있는데, 이 함수는 디스크에서 블록 하나를 읽어들이는 데 사용됩니다.
우리가 블록 번호를 제공하면, 이 함수는 캐시로부터 버퍼를 하나 할당하고 그 디스크 블록을 메모리로 읽어 들인 뒤, 메모리 안의 그 버퍼에 대한 포인터를 반환합니다.

그리고 logwrite라는 함수가 있는데, 이 함수에는 버퍼에 대한 포인터를 넘겨주면, 그 버퍼 안의 데이터를 다시 디스크로 써 줍니다. bread를 호출한 이후에는, 그 버퍼
안의 데이터를 언제든지 읽거나 수정할 수 있습니다. logwrite는 여러 번 호출할 수 있습니다. 즉, 한 번 쓰고 나서 그 버퍼를 더 수정한 뒤 다시 쓸 수도 있습니다. 특정
버퍼를 다 사용하고 나면, 반드시 brelease 함수를 호출해야 합니다. bread 호출과 release 호출 사이 동안에는 해당 버퍼가 잠겨(lock) 있어서, 그 버퍼를
독점적으로 사용하는 것이 보장됩니다. 즉, 그 기간 동안에는 오직 이 스레드만 그 버퍼에 접근할 수 있습니다.

이제 여러 번의 쓰기들이 모여 하나의 트랜잭션을 이루게 됩니다. begin_op 호출은 트랜잭션이 시작하는 지점을 알리는 역할을 하고, 트랜잭션이 끝날 때는 end_op 함수를
호출해야 합니다. 트랜잭션 안에서는 logwrite를 여러 번 호출할 수 있으며, 같은 버퍼에 대해서든 다른 버퍼들에 대해서든 여러 번 호출할 수 있습니다. 이 모든 쓰기들은
하나의 그룹으로 묶입니다.

로깅 시스템은 트랜잭션 안의 모든 쓰기들이 전부 수행되거나, 아니면 전혀 수행되지 않도록 보장합니다. 즉, 전부 또는 전무(all or nothing)입니다.

파일 시스템은 하나의 트리 구조로 된 디렉터리들과, 그 디렉터리들 안에 위치한 여러 파일들로 구성됩니다. 이 모든 것들은 디스크나 USB 드라이브 같은 하나의 단일
장치(device) 위에 있습니다. 디렉터리들은 트리로 조직되어 있는데, 여기에는 사이클이 없고 DAG(Directed Acyclic Graph, 방향 비순환 그래프)도 아닙니다.
DAG는 방향이 있는 비순환 그래프를 뜻합니다. 여기 파일 시스템 예제가 있고, 디렉터리는 빨간색으로, 디렉터리가 아닌 파일들은 초록색으로 표시했습니다. 빨간색만 보면 이 구조가
트리라는 것을 알 수 있습니다. 즉, 루트를 제외한 모든 디렉터리는 부모가 하나뿐입니다. 디렉터리가 아닌 나머지 파일들은 초록색으로 표시했고, 이들 중 일부는 여러 부모를 가지는
것을 볼 수 있습니다.

그리고 기억하다시피, 우리는 파일을 경로 이름(path name)으로 참조합니다. 파일 그 자체는 이름을 가지지 않습니다. 대신, 우리는 그 파일의 경로 이름을 통해 파일을
참조하거나 접근합니다. 예를 들어, 여기 있는 이 파일은 /a/f/k 같은 경로 이름으로 참조할 수 있고, 또 다른 경로 이름을 사용해서 같은 파일을 가리킬 수도 있습니다.

모든 디렉터리 자체도 하나의 파일입니다. 그래서 디렉터리와 일반 파일, 이렇게 여러 다른 타입의 파일이 존재합니다. xv6에는 device라는 파일 타입도 있습니다. 사실 디렉터리
트리 안에 위치한 device는 하나뿐이고, 그것이 바로 콘솔(console)입니다. 하지만 일반적으로는 다른 장치들도 있을 수 있습니다. xv6이 구현하는 파일 타입은 이 세
가지뿐이지만, Unix 시스템과 Linux 시스템은 다른 타입들도 구현합니다. POSIX는 Unix와 Linux 시스템을 위한 표준이고, 이 표준은 다른 종류의 파일도 명시합니다.
그래서 보통 device를 보게 되는데, device에는 실제로 두 가지 종류가 있습니다. 문자 장치(character device)와 블록 장치(block device)가
있습니다. 또 심볼릭 링크(symbolic link, 때때로 soft link라고도 부름), 이름 있는 파이프(named pipe), 소켓(socket) 같은 것도 있습니다.
하지만 이런 것들은 xv6에는 없습니다. 그리고 앞에서 말했듯이, 파일은 이름을 가지지 않고, 우리는 개별 파일을 경로 이름을 사용해 참조합니다.

이제 하드 링크(hard link)와 심볼릭 링크(symbolic link, soft link라고도 함)의 차이에 대해 잠깐 이야기하고 싶습니다. xv6를 포함한 모든 Unix,
Linux 시스템은 하드 링크를 구현합니다. 하지만 xv6는 심볼릭 링크는 구현하지 않습니다. 일반 파일 하나에는 여러 개의 하드 링크가 있을 수 있습니다. 즉, 여러 개의 부모를
가질 수 있습니다. 제가 든 예에서 이 파일은 여러 개의 하드 링크로 참조되고 있습니다. 다시 말해, 이 파일은 이 디렉터리의 엔트리로도, 또 이 디렉터리의 엔트리로도 동시에
존재할 수 있습니다. 반면, 각 디렉터리는 루트 노드를 제외하면 정확히 하나의 부모만을 가집니다. 따라서 각 디렉터리는 하나의 하드 링크만 가질 수 있습니다. 즉, 디렉터리 트리는
반드시 트리 구조여야 합니다. 그러나 디렉터리 외의 다른 파일들을 포함해서 보면 전체 구조는 방향 비순환 그래프가 됩니다.

그래서 xv6에는 일반 파일, 디렉터리, device가 있습니다. 심볼릭 링크는 또 다른 종류의 파일인데, xv6에는 포함되어 있지 않지만, 개념적으로는 하나의 파일 타입입니다.
그렇다면 심볼릭 링크에서는 무슨 일이 일어나는 걸까요?

심볼릭 링크도 일단 “파일”입니다. 하지만 이 파일은 실제 데이터가 아니라 또 다른 경로 이름을 담고 있습니다. 커널이 이 파일을 만나면, 그 안에 들어 있는 경로 이름을 사용해서
우리가 “타깃 파일(target file)”이라고 부를 수 있는 파일을 자동으로 찾아갑니다. 예를 들어, 여기 있는 이 파일이 심볼릭 링크라고 해 봅시다. 이 파일은 직접적인
데이터를 담고 있지 않고, 대신 이 안에는 어떤 경로 이름이 들어 있습니다. 그래서 우리가 이 파일을 경로 이름 c/h로 참조하면, 커널은 이 파일이 심볼릭 링크라는 것을
알아내고, 그 안에 들어 있는 두 번째 경로 이름을 사용합니다. 이 두 번째 경로 이름은 예를 들어 여기 있는 이 파일을 가리킬 수 있습니다. 그러면 read나 write 같은
작업을 할 때 이 파일의 데이터를 읽고 쓰는 것이 아니라, 이쪽에 있는 타깃 파일의 데이터를 읽고 쓰게 됩니다.

하드 링크를 사용할 때 경로 이름은 유효하거나, 아니면 무효합니다. 예를 들어 c/g라고 하면 이 파일까지 올 수 있지만, c/b라고 하면 이 디렉터리 안에 b라는 엔트리가
없으므로 잘못된 경로 이름이 됩니다. 심볼릭 링크에서는 또 다른 상황이 나타납니다. 심볼릭 링크가 “깨질(broken)” 수 있습니다. 즉, 이 심볼릭 링크 파일까지 내려오는 경로
이름 자체는 완전히 유효할 수 있지만, 심볼릭 링크 안에 들어 있는 경로 이름이 존재하지 않는 파일을 가리킬 수 있습니다. 즉, 그 안의 경로 이름이 잘못된 경로일 수 있습니다.

하드 링크의 경우, 파일은 반드시 그것을 가리키는 디렉터리와 같은 파일 시스템, 같은 파일 시스템 안에 있어야 합니다. 그래서 하드 링크로 묶인 것들은 모두 하나의
장치(device) 위에 있게 됩니다. 심볼릭 링크의 장점 중 하나는, 그 안에 들어 있는 경로 이름이 다른 장치, 다른 파일 시스템 위에 있는 파일을 가리킬 수 있다는 점입니다.
그리고 이런 점 때문에 우리가 어떤 작업을 시도할 때 문제가 생길 수도 있습니다.

심볼릭 링크에 또 다른 문제가 되는 경우는, 심볼릭 경로 이름이 가리키는 파일 시스템이 아예 사용 불가능한 상태일 수 있다는 점입니다. 커널이 그 경로를 추적해서 따라가려 해도,
그 파일 시스템이 마운트되어 있지 않거나 이용할 수 없는 상황일 수 있습니다. 이것도 심볼릭 링크에서 생길 수 있는 또 하나의 문제입니다.

다음으로, I number와 inode라는 용어를 정의하고자 합니다. 여러분이 알다시피, 사용자 모드 프로그램은 파일을 경로 이름으로 참조합니다. 하지만 경로 이름은 꼭 유일할
필요도 없고, 바뀔 수도 있습니다. 반면에 커널은 파일을 식별하고 다루기 위해 숫자를 사용하고, 이것을 I number라고 부릅니다. 작은 정수이고, 파일이 생성될 때 그 파일에
할당됩니다. 파일의 생애 동안에는 이 I number는 절대로 변하지 않습니다. 파일이 삭제되면 그 I number는 더 이상 필요하지 않게 되고, 새 파일을 위해 재사용될 수
있습니다. 실제로 그렇게 재사용이 되기도 합니다.

또 한 가지 사실은, 루트 디렉터리는 고정된, 잘 알려진 I number를 가지고 있고, 그 숫자는 1이라는 점입니다. 여기 화면에 있는 건 실수인데, 루트의 I number는
1입니다. 이렇게 되어 있는 이유는 커널이 루트 디렉터리를 찾을 수 있어야 하기 때문입니다. 그리고 파일의 번호 매김은 0이 아니라 1부터 시작합니다. I number 0은
사용되지 않은 디렉터리 엔트리를 나타내기 위해 예약되어 있습니다.

각 파일에는 여러 개의 속성이 연관되어 있는데, 그중 가장 중요한 속성이 바로 각 파일을 유일하게 식별하는 데 사용되는 I number입니다. 그 다음으로 type 필드는 우리가
어떤 종류의 파일을 다루고 있는지를 나타냅니다. xv6에서는 디렉터리 파일, 일반 파일, 또는 디바이스 세 가지 타입이 있습니다. 다른 Unix나 Linux 시스템에서는 여기에
더해 다른 타입들도 존재합니다. 디렉터리와 일반 파일은 데이터를 포함하고 있으므로, 디렉터리나 일반 파일인 경우 우리가 얼마나 많은 데이터를 가지고 있는지 알아야 합니다. 그래서
데이터의 크기를 바이트 단위로 기록합니다.

또한 몇 개의 하드 링크가 이 파일을 가리키고 있는지도 추적해야 합니다. 이것은 트리 구조에서 부모의 개수라고 생각할 수 있습니다. 예를 들어, 이 파일에는 두 개의 하드 링크가
연결되어 있습니다. 만약 하드 링크가 하나도 없다면, 그 파일을 가리키는 경로 이름이 전혀 존재하지 않는 것이고, 따라서 그 파일을 참조할 방법이 없습니다. 그래서 하드 링크의
개수를 참조 카운트(reference count)라고 생각할 수 있습니다. 객체지향 시스템에서 어떤 객체를 가리키는 포인터의 개수가 0이 되면, 가비지 컬렉터가 그 객체의 공간을
회수합니다. xv6 커널에서도 비슷한 일이 일어납니다. 하드 링크의 수가 0이 되는 순간, 커널은 자동으로 그 파일을 삭제합니다.

디렉터리와 일반 파일의 경우에는 추가적인 데이터가 있고, 그렇기 때문에 그 데이터가 디스크의 어디에 저장되어 있는지를 알아야 합니다. 기본적으로, 파일의 데이터를 담고 있는 디스크
블록 번호들의 리스트를 가지고 있습니다. xv6가 아닌 다른 Unix/Linux 시스템에서는, 여기에 더해 추가 정보가 있습니다. 예를 들어 파일이 언제 생성되었는지, 마지막으로
언제 수정되었는지 등의 타임스탬프가 있고, 누가 이 파일의 소유자인지에 대한 정보, 그리고 다른 사용자가 이 파일에 어떻게 접근할 수 있는지를 나타내는 퍼미션 비트들도 있습니다.

이러한 속성들은 디스크 상에서 inode라고 불리는 작은 고정 크기 구조체 안에 저장됩니다. inode는 디스크에 저장되어 있으며, 어떤 파일 안에 들어 있는 것이 아니라 디스크의
별도 영역에 저장됩니다. 즉, 디스크 어딘가에 I number로 인덱스되는 inode 구조체의 배열이 존재하는 셈입니다.

어떤 파일이 커널에 의해 사용 중일 때는, 커널이 디스크로부터 그 파일의 inode 구조체를 읽어 들여 메모리에 유지해야 합니다. 그래서 커널은 메모리 안에 inode의 캐시를
유지합니다. 이제 디스크 상에서 inode 구조체가 어떻게 정의되어 있는지 살펴보겠습니다.

여기 보이는 구조체가 디스크 상의 inode를 나타냅니다. 여기에는 I number가 보이지 않는데, 앞에서 말한 것처럼 이 inode들은 I number로 인덱스되는 배열 형태로
저장되기 때문에, I number는 암묵적으로 정해집니다. type 필드는 이것이 어떤 종류의 파일인지를 알려줍니다. 디렉터리인지, 일반 파일인지, 디바이스인지 나타내기 위한 여러
상수가 있습니다. 또한 이 type 코드를 이용해서 inode가 사용 중인지 여부도 나타냅니다. 디스크의 inode 배열에 있는 inode들 중 일부는 실제로 사용 중이며, 타입이
디렉터리, 파일, 혹은 디바이스입니다. 그러나 나머지 inode들은 비어 있고 아직 사용되지 않았으며, 미래의 파일을 위해 남겨진 것들입니다. 이런 inode들의 type은 0으로
설정합니다.

파일이 디바이스인 경우, major와 minor 번호도 유효한 값이 됩니다. 그럼 major와 minor 번호는 무엇일까요? 이는 본질적으로 디바이스 번호입니다. 디바이스 번호는
32비트 숫자이고, 두 개의 16비트 필드인 major 번호와 minor 번호로 나뉩니다. major 번호는 이게 어떤 종류의 디바이스인지를 나타내는 식별자이고, minor 번호는
여러 개의 디바이스 중에서 어느 개체인지를 나타냅니다. 예를 들어 Hewlett-Packard 프린터가 세 대 있다고 해봅시다. major 번호는 “이것은
Hewlett-Packard 프린터다”를 나타내며, 어떤 루틴을 사용해 이 프린터에 접근해야 하는지를 결정하는 데 쓰입니다. minor 번호는 이것이 1번, 2번, 3번 프린터 중
어느 것인지를 나타냅니다.

그 다음 필드가 하드 링크의 개수이고, 디렉터리나 일반 파일인 경우에는 바이트 단위의 크기가 나옵니다. 마지막으로, 디렉터리나 일반 파일인 경우, 그 데이터가 저장될 디스크 상의
블록 번호들이 필요합니다. 여기 보이는 것이 바로 블록 번호들의 배열입니다.

이전에 디스크 로깅을 설명할 때, 디스크가 어떻게 생겼는지에 대한 개략적인 다이어그램을 보여주었는데, 그때는 여기 메인 블록 영역만 그려두었습니다. 이제는 그보다 더 정확하고
자세한 디스크 구조를 보여주고자 합니다. 이 그림을 차례대로 살펴봅시다.

맨 먼저 boot record가 있는데, 이 블록은 커널에 의해 읽거나 수정되지 않습니다. 부팅과 시작 과정에서 커널을 메모리로 적재하기 위해서만 사용됩니다. super
block에는 여러 매개변수가 들어 있으며, 커널이 읽기는 하지만 수정하지는 않습니다. 이 안에는 디스크 상의 다른 항목들이 어디에 있는지를 알려주는 정보 등이 들어 있습니다.

그 다음이 log인데, 이것은 다른 곳에서 이미 설명했으므로 여기서는 더 이상 자세히 다루지 않겠습니다. 그 다음 영역에는 inode 구조체들이 저장되고, 그 다음에 bitmap,
그리고 data block들이 있습니다.

각 inode는 고정 크기 구조체로 저장되고, 이 구조체들은 배열 형태로 연속해서 저장됩니다. 그리고 이 배열이 여러 개의 블록 안에 들어 있습니다. 각 블록에는 소수의
inode만 들어갈 수 있기 때문에, 사용 중인 inode와 아직 비어 있는 inode 전체를 포함해 inode의 총 개수에 따라, inode 저장만을 위해 할당된 블록들이 여러
개 필요합니다.

그 다음에 bitmap이 있습니다. bitmap은 디스크의 각 블록마다 한 비트씩을 가지고 있으며, 그 블록이 사용 중인지, 비어 있는지를 나타냅니다. 특히 data block들을
관리하는 데 매우 유용합니다. 여기까지의 블록들은 전부 사용 중인 블록으로 간주합니다. 따라서 bitmap에서는 이 지점까지의 모든 블록이 사용 중이라는 표시가 들어 있고, 그
이후의 블록들은 각각 사용 중이거나 비어 있는 상태인데, 그 정보가 bitmap의 비트로 표현됩니다.

요약하면, 이 파일 시스템의 모든 블록마다 하나의 비트가 존재합니다. 이 특정 파일 시스템에서는 블록이 1000개뿐입니다. 따라서 이 bitmap은 1000개의 비트를 담을 수
있을 만큼만 크면 되고, 당연히 한 블록 안에 전부 들어갈 수 있습니다. 여기에서는 설명을 위해 세 블록을 그려두었을 뿐입니다. 각 비트 값이 1이면 그 블록이 사용 중이라는
뜻이고, 0이면 그 블록이 비어 있다는 뜻입니다.

비어 있다는 뜻이고, 마지막으로 데이터 블록들이 있습니다. 여기에는 실제 파일과 디렉터리가 저장됩니다.

이제 superblock을 보겠습니다. superblock은 기본적으로 여기 보이는 이 구조체 한 블록을 디스크에 담아 놓은 것입니다. 이 구조체에는 여러 개의 필드가 있습니다.
이 블록에 디스크 상에 어떤 내용이 저장되는지 보겠습니다. 먼저 매직 넘버가 있습니다. 이건 그냥 상수이고, 운영체제가 superblock을 읽어 들였을 때 이 숫자를 검사해서
올바른 값인지 확인합니다. 값이 다르면 “이건 우리가 기대하는 종류의 파일 시스템이 아닌데?” 혹은 “뭔가 큰 문제가 있다, 이 디스크는 아예 파일 시스템을 담고 있지 않다” 같은
상황을 의미할 수 있습니다.

우리 예제에서 size 필드는 1000입니다. 디스크에 사용할 수 있는 블록이 몇 개인지를 알려 줍니다. 데이터 블록의 개수는 우리 경우 959입니다. 그러니까 여기 데이터 블록이
그만큼 있고, inode는 200개가 있습니다. 그럼 이게 블록으로 몇 개인가? 그건 커널이 계산해서 알아낼 겁니다. 어쨌든 200개의 inode를 저장할 수 있는 충분한 공간이
있고, 이는 이 파일 시스템이 최대 200개의 파일을 수용할 수 있다는 뜻입니다. 200개보다 더 많은 파일은 가질 수 없습니다.

log는 로그에 할당된 블록의 개수이고, 그 다음에 로그가 어디서 시작하는지 나타내는 값이 있습니다. 로그는 블록 번호 2에서 시작합니다. 그리고 inode가 어디서 시작하는지,
블록 번호 32에서 시작하고, bitmap은 블록 번호 38에서 시작합니다.

bitmap의 크기는 블록 개수에 의해 결정됩니다. 앞에서 말했듯이 블록이 1000개라면 bitmap을 실제로는 한 블록에 다 집어넣을 수 있습니다. 다만 여기에서는 이해를 돕기
위해 3개를 그려놓았을 뿐 실제로는 그렇지 않습니다. 이 superblock은 부팅 시에 readsb라는 함수가 디스크에서 읽어 들이고, 그 뒤로는 변하지 않습니다.

여기에 그 내용을 담는 구조체를 보여주고 있는데, 방금 본 것과 정확히 같습니다. 매직 넘버가 있고, 블록 단위 크기(size), inode 개수, log에 포함된 블록 개수,
로그 시작 위치, inode 블록의 시작 위치, bitmap 블록의 시작 위치가 있습니다. 이것들이 부팅 시에 읽혀 들어옵니다.

제가 예제 파일 시스템을 보여줄 때는 그래프의 간선을 라벨링해서 표시했는데, 이것도 중요합니다. 경로 이름(path name)을 강조하기 위해서죠. 하지만 여러분이 디렉터리를 그런
방식으로 생각하지 않을 수도 있습니다. 여기서는 간선에 이름을 적어 놓았지만, 어떤 사람은 디렉터리를 “이름들의 모음이고, 각 이름이 어떤 디렉터리나 파일을 가리킨다”라고 생각할
수도 있습니다.

디렉터리는 파일로 저장됩니다. 그러니까 모든 디렉터리마다 하나의 파일이 있고, 그 파일이 여러 개의 블록을 가집니다. 디렉터리 정보는 그 블록들 안에 저장됩니다. xv6에서는
디렉터리가 이렇게 되어 있습니다. xv6에서 디렉터리는 배열로 표현되고, 배열의 각 엔트리는 이름과 파일에 대한 참조 둘 다를 가지고 있습니다. 이름은 최대 14개의 문자까지
저장할 수 있고, 파일에 대한 참조는 inode 번호(i-number)입니다. 원래 유닉스 시스템에서도 파일 이름은 14자 제한이 있었습니다. xv6에서도 파일 이름은 최대
14자까지이고, 더 짧으면 문자열 끝에 널 문자(null)를 넣어 끝을 표시합니다.

어떤 파일을 찾아야 할 때는 이 배열을 앞에서부터 차례대로(linear) 훑어야 하고, 이건 시간이 좀 걸립니다. 현대 Unix와 Linux 시스템은 더 긴 파일 이름을 지원하고,
또 어떤 디렉터리는 수백 개의 파일을 포함하기 때문에 디렉터리를 위해 다른 조직 방식을 씁니다. 더 빠르게 검색할 수 있는 다른 자료구조들을 사용합니다. 하지만 본질적인 아이디어는
똑같습니다. 이름이 있고, 각 이름마다 하나의 inode 번호가 있는 구조입니다.

이 정도면 파일 시스템이 디스크 위에 어떻게 저장되는지에 대한 설명은 거의 마무리되었습니다. 이제 다음으로 mkfs 함수, 혹은 프로그램을 보겠습니다. 이 프로그램은 파일 시스템을
처음부터 새로 만드는 데 사용됩니다.

mkfs, 혹은 “make file system” 프로그램은 독립적인 C 프로그램입니다. xv6 커널의 일부가 아니고, xv6 커널 위에서 돌아가는 사용자 모드 프로그램도
아닙니다. 완전히 별도의 C 프로그램이고, 여러분의 호스트 컴퓨터에서 컴파일되어, QEMU 에뮬레이터처럼 그 호스트 컴퓨터에서 실행됩니다. make 파일을 실행하면 xv6 커널을
컴파일하고, 모든 사용자 모드 프로그램들을 컴파일하며, 이 mkfs 프로그램도 컴파일해서 실행합니다.

이 “make file system” 프로그램은 무엇을 하느냐 하면, 디스크 이미지 파일을 만듭니다. 디스크 이미지 파일의 이름은 fs.image이고, 이는 호스트 컴퓨터 위의
일반 파일입니다. QEMU는 이 파일을 사용해 디스크를 에뮬레이션합니다. 디스크의 모든 내용은 이 파일 시스템 이미지 파일 안에 들어 있고, 디스크에 대해 읽기/쓰기 요청이 있을
때마다 QEMU가 실제로 호스트 시스템의 이 파일에 접근해서 데이터를 읽고 쓰게 됩니다.

xv6에서의 디스크는 블록이 1000개로 초기화되어 있고, 각 블록은 1024바이트입니다. 따라서 이 파일 크기는 1000KB, 즉 에뮬레이션된 디스크의 각 바이트마다 파일에
1바이트가 있는 구조입니다. make file system 프로그램은 디스크를 초기화합니다. 즉, 전체 파일 시스템을 만들어 냅니다. 디렉터리 트리를 만들고, 그 디렉터리 트리에
여러 개의 파일을 집어넣습니다. 그래서 커널이 시작될 때, 즉 부팅 시점에 이미 파일 시스템이 존재하는 상태가 됩니다.

무엇을 하느냐 하면, make file system은 superblock을 파일(정확히 말하면 이미지 파일)에 씁니다. 부트 레코드에 대해서는 아무것도 쓰지 않습니다. 필요하지
않기 때문입니다. 그리고 모든 inode를 초기화하고, 에뮬레이트된 디스크의 bitmap 영역을 초기화합니다. 디렉터리 구조를 만들고 몇 개의 디렉터리를 초기화합니다. 그리고 각
사용자 파일, 즉 cat, echo, 초기 프로그램(init), shell 같은 사용자 모드 실행 파일마다 하나씩 파일을 만들고, 그것들을 파일 시스템의 디렉터리에 추가합니다.

그래서 make file system이 끝났을 때 이 이미지 파일에는 완전한 파일 시스템 전체가 들어 있게 되고, 커널이 부팅해서 바로 이 파일 시스템을 찾을 수 있습니다.

실제 Unix와 Linux 시스템에도 make file system이라는 비슷한 프로그램이 있고, 이들은 이미지 파일이 아니라 장치(device)를 초기화합니다. 그리고 그 장치
위에 파일 구조를 조직하기 위해 필요한 것들을 모두 씁니다. 우리가 xv6에 대해 이야기한 파일 시스템 조직은 꽤 단순한 편이고, 다른 시스템들의 make file system
프로그램은 훨씬 다르고 복잡한 파일 시스템을 만들어 냅니다. 그래서 실제 장치 위에 최초의 파일 시스템을 만드는 이런 프로그램들은 꽤 복잡합니다.

어쨌든 xv6에서 우리가 보고 있는 make file system 프로그램은 몇 가지 매개변수를 사용합니다. param.h 파일로 가서 파일 시스템 크기(파일 시스템에 몇 개의
블록을 만들 것인지), 그리고 log에 추가할 블록 수 같은 것들을 가져옵니다. 또 여러 미리 정의된 매개변수, 매크로, 상수들도 있습니다. 예를 들어 블록 수 같은 것들이
있습니다.

비트맵에 대해 한 블록에 저장할 수 있는 비트 수라든지, 디스크에 표현될 inode 배열 안의 한 블록에 얼마나 많은 inode를 집어넣을 수 있는지 같은 것들이 있습니다. 이
상수들은 이미지 파일을 생성하는 makefilesystem.c 프로그램에 의해 필요하게 됩니다.

자, 여기까지로 마무리하겠습니다. 다음 비디오에서 다시 보겠습니다.
