## 한국어 번역

이 비디오는 xv6 운영체제 커널에 대한 연속 강의의 일부입니다. 이 비디오에서는 RISC-V 아키텍처에 대해 이야기할 것이고, 특히 status 레지스터와 트랩이 하드웨어에서
어떻게 처리되는지에 초점을 맞추겠습니다. 기억을 되살려 보면, 우리가 쓰는 용어에 따르면 트랩에는 두 종류가 있는데, 예외와 인터럽트입니다. 시스템 콜은 예외의 한 종류이고,

어떤 종류의 프로그램 오류도 예외입니다. RISC-V에서 시스템 콜 명령어는 ecall이고, 프로그램 오류에는 불법 명령어, 정렬 오류(alignment error) 등 여러
가지가 포함될 수 있습니다. 또 장치들이 인터럽트를 발생시킬 수도 있습니다. 인터럽트는 우리가 사용자 모드나 supervisor 모드에서 실행 중일 때 발생할 수 있고, 어떤
모드에서 인터럽트가 발생하든 항상

supervisor 모드에서 실행되는 핸들러 코드로 진입하게 됩니다. stvec은 하나의 control and status register(CSR)이고, 핸들러 코드에 대한
포인터를 담고 있습니다. 구체적으로 말하면, 어떤 트랩이 발생했을 때 그것을 처리할 코드의 첫 번째 명령어 주소를 담고 있습니다. xv6에는 트랩을 처리하는 코드가 두 군데
있습니다. kernelvec은 supervisor 모드에서 실행 중에 발생한 트랩을 처리하고,

uservec은 사용자 모드 코드가 실행 중일 때 발생한 트랩을 처리합니다. 그러면 status 워드부터 시작하겠습니다. 여기서는 supervisor 모드에서 실행 중인 코드가
보게 될 status 워드, 즉 sstatus에 초점을 맞추겠습니다. xv6 커널은 거의 전부 supervisor 모드에서 실행되기 때문에 우리가 신경 써야 할 status 워드는
이것입니다. 실제로는 제가 설명하는 것보다 약간 더 복잡하지만,

여기서는 세 비트만 다루겠습니다. xv6 커널을 이해하는 데는 그것이면 충분하다고 생각합니다. 첫 번째는 인터럽트가 활성화되어 있는지 여부를 제어하는 비트이고, 이 비트의 이름은
인터럽트 활성화를 의미하는 SIE입니다. 인터럽트가 발생하면 이 비트의 값을 저장해야 하고, 이 값은 status 워드의 또 다른 비트인

SPIE, 즉 이전 인터럽트 활성 비트(previous interrupts-enabled bit)에 저장됩니다. 또 하나 기억해야 할 것은 트랩이 발생했을 때 우리가 어떤 모드에서
실행 중이었는지입니다. 사용자 모드에서 실행 중이었을 수도 있고, supervisor 모드에서 예외가 발생했을 수도 있습니다. 트랩은 예외나 인터럽트의 결과로 발생할 수 있습니다.
물론 인터럽트라면 그 이전 값은 활성 상태였을 것입니다. 그렇지 않았다면

우리가 그 인터럽트를 처리하고 있지 않을 테니까요. 하지만 인터럽트가 비활성화된 상태에서 예외가 발생할 수도 있습니다. 어떤 경우든, 우리가 인터럽트된 코드로 되돌아갈 때 이
비트를 이전 상태로 복원할 수 있도록 그 이전 값을 저장해 두어야 합니다. 커널에서 쓰는 한 가지 기법은 인터럽트 활성 비트를 잠시 바꿔서 모든 인터럽트를 비활성화하는 것입니다.

이렇게 하면 특정 임계 구역(critical section)을 다른 스레드가 방해하지 못하게 할 수 있습니다. 다만 xv6는 멀티코어 운영체제이기 때문에, 이 기법은 다른 코어가
무엇을 하고 있는지에 대해서는 아무런 영향을 주지 않습니다. 다른 코어들은 동시에 메모리를 변경하고 있을 수도 있습니다. 그러한 상황을 처리하기 위해서 우리는 락을 사용합니다.
그러나 인터럽트 비활성화 자체도 커널 안에서 사용됩니다. 자, 트랩이 발생하면

무슨 일이 벌어질까요? 먼저 물어봐야 할 질문은 인터럽트가 활성화되어 있는가 비활성화되어 있는가 입니다. 만약 인터럽트가 비활성화되어 있다면, 트랩은 펜딩 상태로 남습니다. 즉,
하드웨어에서 즉시 처리되지 않고, 커널이 나중에 인터럽트를 다시 활성화할 때까지 핸들러 코드는 실행되지 않습니다. 그리고 그 시점에서 트랩 처리가 일어납니다. 반면, 예외의
경우에는

인터럽트 비활성화 여부와 상관없이 즉시 처리됩니다. 하지만 어느 경우든 트랩이 실제로 처리될 때 하드웨어는 다음과 같은 일을 하고, 그 다음 다시 실행을 이어갑니다. 먼저 이전
명령어를 완료한 후, program counter(PC)의 복사본을 sepc라는 control and status register에 저장합니다. 그 다음 stvec에 저장된 값을
program counter에 복사해서

핸들러 코드의 첫 번째 명령어로 분기합니다. 이어서 scause 레지스터에, 어떤 일이 일어났는지, 즉 어떤 이유로 트랩 핸들러가 호출되었는지에 대한 정보를 저장합니다. 그리고
stval이라는 CSR에 추가 정보를 저장할 수 있습니다. xv6 커널에서 우리가 관심을 가질 몇 가지 원인 값이 있습니다. 시스템 콜인 경우 cause 값은

8이 됩니다. 외부 장치로부터의 인터럽트인 경우 9가 됩니다. 소프트웨어 인터럽트인 경우에는 1이 되는데, 이것들은 타이머 인터럽트와 관련이 있고, 곧 설명하겠습니다. 그 밖의
모든 것은 프로그램 예외이며, 코드 안의 어떤 종류의 오류입니다. 하드웨어는 예외나 인터럽트가 발생했을 때 우리가 사용자 모드에서 실행 중이었는지 supervisor 모드에서 실행
중이었는지를 즉시 저장하고,

그 정보는 status 워드의 이 비트에 저장됩니다. 그리고 인터럽트 활성 비트의 이전 값도 SPIE에 저장합니다. 마지막으로 하드웨어는 인터럽트를 비활성화하고, 이미
supervisor 모드가 아니었다면 모드를 supervisor로 변경합니다. 이 시점에서 트랩 처리의 하드웨어 단계는 끝나고, 우리는

핸들러 코드의 첫 번째 명령어를 실행하기 시작합니다. 핸들러 코드는 여러 가지 일을 할 텐데, 구체적으로는 커널 코드를 보면서 살펴보겠습니다. 그리고 어느 시점이 되면, 우리가
인터럽트된 코드로 돌아갈 준비가 될 것입니다. 이를 위해서 우리는 RISC-V 명령어 sret, 즉 supervisor 모드로부터의 복귀 명령을 사용합니다. 이 명령어는 저장해
두었던 복사본으로부터 인터럽트 활성 비트를 복원하고,

이전에 우리가 실행 중이던 모드로 돌아가며, program counter를 인터럽트가 발생하기 전의 값으로 복원합니다. 그리고 나서 인터럽트되었던 코드의 실행을 재개합니다.
지금까지가 supervisor 모드에서 일어나는 일이고, 커널 대부분은 supervisor 모드에서 실행됩니다. 하지만 커널의 극히 일부는 machine 모드에서 실행되고,

이제 machine 모드에서의 트랩 처리에 대해 이야기하겠습니다. 개념은 본질적으로 동일합니다. mstatus라는 또 다른 레지스터가 있습니다. 사실 이 레지스터는 sstatus와
거울처럼 같은 레지스터일 수도 있습니다. 구현 상으로는 한 레지스터로 되어 있을 수도 있지만, 우리의 관점에서는 별개의 레지스터라고 생각해도 무방합니다. 그리고 sstatus
레지스터와 마찬가지로, 이 레지스터에도 인터럽트 활성/비활성 제어 비트와

이전 인터럽트 활성 값 저장용 비트가 있으며, 마지막으로 이전 모드 레벨을 저장하는 필드가 있습니다. 트랩이 발생했을 때 우리가 사용자 모드, supervisor 모드,
machine 모드 중 어느 모드였는지를 저장해야 하므로, 이를 위해 두 개의 비트를 사용합니다. 우리가 machine 모드에서 실행 중이라면 supervisor 모드로의
인터럽트는 발생하지 않습니다. 인터럽트와 트랩은 위쪽 방향으로만 진행되기 때문에,

machine 모드용으로 두 비트가 필요하지만, supervisor 모드 인터럽트에는 한 비트만 있으면 됩니다. supervisor 모드로 내려올 때는 machine 모드에서 올
수 없으니까요. 우리가 machine 모드 수준에서 처리하는 유일한 인터럽트는 타이머 인터럽트이고, 나머지 모든 트랩, 즉 다른 모든 인터럽트와 예외는 supervisor 모드에서
처리하도록 위임(delegation)하는 메커니즘을 가지고 있습니다.

타이머 인터럽트를 위임할 것이기 때문에, 그것이 소프트웨어 인터럽트라고 불리는 어떤 것으로 변형(mutate)되는 모습을 보게 될 겁니다. 인터럽트는 항상 machine mode
수준에서 활성화되어 있습니다. 그래서 트랩, 아니, 타이머 인터럽트가 발생할 때마다 그것은 처리됩니다. 그 외의 다른 종류의 트랩이 발생하면, 자동으로 supervisor mode
로 위임되고, 그것이 즉시 처리될지 아니면 pending 상태가 될지는 supervisor mode 수준에서 인터럽트가 활성화되어 있는지 비활성화되어 있는지에 의해 결정됩니다.

타이머 인터럽트가 발생하면 machine mode 핸들러가 실행되고, 그 코드는 소프트웨어 인터럽트라고 불리는 것을 생성하거나 강제로 만들어냅니다. 그리고 그 소프트웨어 인터럽트가
supervisor mode 코드에 인터럽트를 걸 겁니다. machine mode 에서 돌아가는 핸들러 코드는 계속 실행되다가 인터럽트를 다시 활성화하고, 인터럽트되었던 코드로
되돌아갑니다. 만약 인터럽트되었던 코드가 supervisor 코드였다면 supervisor mode 로 돌아갈 것이고, 인터럽트되었던 코드가 사용자 프로그램이었다면 그 프로그램으로
돌아갑니다. supervisor 수준에서 인터럽트가 활성화되어 있다면, 그 수준에서 인터럽트가 즉시 발생할 겁니다. 반대로 커널이 잠깐 supervisor mode 수준에서
인터럽트를 비활성화했다면, 커널이 그것을 처리할 준비가 될 때까지 그 인터럽트는 pending 상태로 남습니다.

machine mode 수준의 트랩 처리도 거의 같은 방식으로 일어납니다. 제가 말했듯이 개념은 완전히 같습니다. 인터럽트의 유일한 원인은 타이머 인터럽트이고, 그 외의 모든
종류의 인터럽트는 하드웨어 수준에서 즉시 supervisor mode 로 위임되기 때문에, 우리는 타이머 인터럽트 이외의 것에 대해서는 이런 처리를 하지 않습니다.

stvec 레지스터처럼, mtvec 레지스터도 있는데, 여기에는 machine mode 트랩 핸들러의 주소가 들어 있습니다. xv6 에서는 그 코드는 timervec 이라는
함수이고, 타이머 인터럽트를 처리합니다. 하드웨어는 직전 명령어를 완료한 뒤 다음과 같은 동작을 수행합니다. 우선 프로그램 카운터를 mepc 라는 레지스터에 저장합니다. 그리고
프로그램 카운터에 mtvec 값을 적재해서, 핸들러로 점프하도록 만듭니다. mcause 와 mtval 레지스터는 무시됩니다. 이것은 타이머 인터럽트이고, 우리가 관심 있는 추가
정보는 없습니다. 하드웨어는 이전 모드, 즉 우리가 user mode 에 있었는지, supervisor mode 에 있었는지, machine mode 에 있었는지를 저장하고, 그
값을 두 비트에 저장합니다. 그리고 이전의 “인터럽트 활성화 여부” 비트 값을 이 비트에 저장한 다음, 인터럽트를 비활성화하고 machine mode 로 전환합니다.

그 다음 timervec 코드가 실행됩니다. 이 코드는 무엇을 할까요? supervisor 수준에서 인터럽트를 합성(synthesize)하거나 발생시킬 겁니다. 즉,
supervisor 수준에서의 인터럽트를 만들어내는 어떤 동작을 수행할 것입니다. 이때 생성되는 인터럽트는 타이머 인터럽트가 아니라, 이른바 소프트웨어 인터럽트입니다. 그리고
비교적 짧은 이 코드는 mreturn 이라는, machine mode 용 리턴 명령어를 실행합니다. 이 명령어는 인터럽트 활성화 비트를 원래대로 복구하고, 모드도 이전 모드로
복구하고, 프로그램 카운터도 복구해서, 인터럽트되었던 코드로 되돌아갑니다.

그 다음에 무슨 일이 일어날까요? 방금 소프트웨어 인터럽트를 일으켰고, 그 뒤에 어떤 일이 벌어질지는 supervisor mode 수준에서 인터럽트가 활성화되어 있는지 비활성화되어
있는지에 달려 있습니다. 인터럽트가 비활성화되어 있다면, 소프트웨어 인터럽트는 pending 상태가 되고, 커널이 인터럽트를 활성화할 준비가 될 때까지 그냥 기다려야 합니다.
인터럽트가 활성화되어 있다면, 트랩은 supervisor 수준에서 즉시 발생합니다.

우리는 machine mode 에서 인터럽트를 활성화하는 mie 비트가 있고, supervisor mode 수준에서 인터럽트를 활성화하거나 비활성화하는 ssie 비트가 있습니다.
이 비트들은 전역적인 인터럽트 활성화 비트입니다. 즉, 상태 레지스터의 이 비트들을 바꾸면 모든 인터럽트를 통으로 켜거나 끌 수 있습니다.

또한 RISC 아키텍처에는 좀 더 선택적인 제어를 위한 장치도 있습니다. 꼭 필요한 것은 아니지만, 해당 레지스터들이 존재하고 초기화 과정에서 건드려지기 때문에 설명하겠습니다.
machine mode 인터럽트 활성화용인 mie 는 하나의 레지스터입니다. 약간 헷갈리는데, 상태 워드(status word) 안에 mie 라는 비트가 하나 있고, 또 별도로
mie 레지스터가 있습니다. 마찬가지로 상태 레지스터 안에 sie 라는 비트가 있고, 여기 보이듯이 sIE 가 있지만, 선택적인 제어를 위해 sie 라는 별도 레지스터도 있습니다.
이들은 서로 다른 것들입니다.

선택적 제어를 위해 여러 비트들이 있지만, 우리가 관심 있는 것은 이 한 비트입니다. 이것은 machine mode timer interrupt enable 을 의미하고, 초기화
단계에서 이 값을 1로 설정합니다. 이 동작은 machine mode 에서 실행되는 start 함수 안에서 일어납니다.

supervisor mode 수준에서도 선택적으로 인터럽트를 활성화 또는 비활성화하는 방법이 있고, 그것은 sie 레지스터를 통해 이루어집니다. 우리가 관심 있는 비트는 세
개입니다. 하나는 디바이스 인터럽트, 즉 하드웨어 디바이스로부터의 인터럽트를 활성화 또는 비활성화하는 비트이고, 하나는 소프트웨어 인터럽트를 활성화 또는 비활성화하는 비트이고,
하나는 타이머 인터럽트용 비트입니다. 그런데 이 타이머 인터럽트 비트는 여기서는 왜 사용 불가능한지 잘 모르겠습니다. 타이머 인터럽트를 여기 아래로 위임할 수는 없어 보입니다.
어쨌든 이 비트가 있다는 점만 언급하고 넘어가겠습니다. 초기화 과정에서는 이 비트들을 모두 1로 설정할 것입니다.

또한 sip 라는, pending 상태의 인터럽트를 나타내는 레지스터가 있습니다. 포맷은 방금 것과 동일합니다. 어떤 디바이스가 인터럽트를 걸고 있으면, 해당 비트가 1로 바뀌고,
인터럽트가 pending 상태라는 뜻입니다. 인터럽트가 없으면 0입니다. 우리는 이 비트를 1로 설정함으로써 인터럽트를 pending 상태, 또는 실제 발생 상태로 강제로 만들 수
있습니다. machine mode 에서 실행 중인 timervec 코드는 바로 이 일을 합니다. timervec 은 sip 레지스터 안의 이 비트를 1로 설정해서, 소프트웨어
인터럽트가 발생하도록 강제합니다. 여기서 말하고 있는 것은, machine mode 에서 실행 중인 타이머 인터럽트 핸들러가 ssie 비트를 1로 설정하고, 그 결과 커널 수준의
supervisor mode 에서 소프트웨어 인터럽트가 발생하게 된다는 것입니다.

이제 우리는 트랩을 위임(delegate)할 수 있는 기능을 갖게 되었습니다. 트랩이란 인터럽트 또는 예외(exception)를 의미합니다. RISC 아키텍처에서는 모든 트랩이
원칙적으로 machine mode 핸들러로 갑니다. 하지만 machine mode 핸들러를 건너뛰고, supervisor mode 에서 실행되는 핸들러로 곧바로 가게 하는 기능도
있습니다. xv6 가 바로 이 기능을 사용해서 모든 트랩을 supervisor mode 로 위임합니다. 원래대로라면 machine mode 에서 돌아가는 핸들러가 트랩을 처리했을
테지만, 우리는 그것을 supervisor mode 로 위임할 것입니다.

예외를 위임하는 데 쓰이는 medeleg 레지스터와, 인터럽트를 위임하는 데 쓰이는 mideleg 레지스터 두 개가 있습니다. xv6 는 이 두 레지스터의 비트들을 설정해서 트랩을
위임합니다. 그래서 인터럽트나 예외가 발생하면, 곧바로 supervisor mode 에서 처리되도록 만드는 것입니다.

커널 코드 입장에서는, 어떤 이유에서인지 타이머 인터럽트는 위임(delegation)될 수 없습니다. 그래서 앞에서 말했듯이, 타이머는 소프트웨어 인터럽트 방식을 써서 약간 다르게
처리합니다. 이 두 레지스터, 즉 medeleg 과 mideleg 은 부팅 시점에 초기화되는데, 이 작업은 machine 모드에서 실행되는 start 함수 안에서 이루어집니다. 이
레지스터들은 1로 설정되고, 한 번 설정되면 트랩이 발생했을 때까지 절대 바뀌지 않습니다.

이 인터럽트와 예외들이 위임되기 때문에, machine 모드에서는 아무 일도 일어나지 않고, 바로 supervisor 레벨의 인터럽트나 예외가 됩니다. 이제 이 레지스터들을 짚고
넘어가죠. 여기 보이는 레지스터가 예외를 위임하기 위한 레지스터이고, 다음 슬라이드에는 인터럽트를 위임하기 위한 레지스터가 나옵니다. 그리고 여러 종류의 예외들이 발생할 수
있습니다.

store, load, 명령어 페치에 대한 페이지 폴트가 있고, 환경 호출, 즉 시스템 콜이 있고, 여러 종류의 access fault 가 있습니다. misalignment 와
관련된 fault 도 있고, 명령어가 illegal 한데 그것을 실행하려 하면 그에 대한 예외도 생깁니다. 이런 식으로 여러 가지가 있습니다. medeleg 레지스터를 설정하기
위해 실행되는 명령어가 하나 있고,

본질적으로는 모든 비트를 1로 설정하는 것입니다. 여기 보이는 것은 완전히 합법적인 어셈블리 코드는 아니지만, 아이디어는 전달될 겁니다. 제어 및 상태 레지스터인 medeleg 에
모든 비트가 1인 값을 쓰는 것이죠. 인터럽트 위임을 위해서는 mideleg 이라는 레지스터가 있고, 여기에 몇 개의 비트가 들어 있습니다. 이 레지스터를 통해 디바이스 인터럽트를
위임할 수 있고, 또한

타이머 인터럽트를 위임할 수 있는 기능도 있습니다만, 어떤 이유에서인지 실제로는 그렇게 할 수 없습니다. 어쨌든 간에, 여기서도 비트들이 1로 설정됩니다. 그리고 소프트웨어
인터럽트도 마찬가지로 위임할 수 있습니다. 초기화 코드는 아주 단순해서, 기본적으로 이 모든 비트들을 1로 설정할 뿐입니다. 전체적으로 이런 식으로 동작합니다. 자, 이 비디오는
