이제 다음으로, 이 pipe 구조체가 어떻게 사용되는지 이야기해 봅시다. 프로세스 p가 하나 있다고 가정하겠습니다. 모든 프로세스는 proc 구조체로 표현되고, 여기 보이는 이
객체가 프로세스 p를 나타냅니다. 하나의 프로세스는 동시에 여러 개의 파일을 열어 둘 수 있습니다. 사용자 코드에서는 개별 파일들을 파일 디스크립터로 참조합니다. 파일 디스크립터는
0, 1, 2 같은 작은 숫자이고, 커널이 이 배열에 접근할 때 인덱스로 사용됩니다. 그래서 proc 구조체 안에는 ofile 배열이 있고, 이 배열에는 file 객체들을 가리키는
포인터가 들어 있습니다. 열린 파일마다 이 배열에 포인터가 하나 있고, 그 포인터가 해당 file 객체를 가리킵니다. 물론 사용자 프로세스는 커널 공간의 포인터를 직접 사용할 수
없고,

대신 파일 디스크립터 숫자를 넘깁니다. 예를 들어 파일 번호 2에서 읽고 싶다면, 2를 인자로 넘기고, 커널은 그 숫자를 이용해 이 file 구조체를 찾아 들어갑니다. 그림에서는
모든 파일 디스크립터가 사용 중인 것처럼 보이지만, 실제로는 어떤 파일들은 닫혀 있을 테고, 그 엔트리는 사용되지 않으므로 그 자리에 null이 저장되어 있을 수 있습니다.
file 객체는 type 필드로 시작합니다.

지금은 파이프에 대해 이야기하고 있으므로, 이 예에서의 타입은 pipe입니다. 하지만 대부분의 경우 file 구조체는 inode를 가리키게 됩니다. 어쨌든 file 구조체들은 어떤
객체를 가리키는 포인터를 하나 가지고 있고, 그 포인터가 어떤 객체를 가리킵니다. 그 객체는 파이프일 수도 있고 inode일 수도 있습니다. 보통 일반 파일이나 디렉터리의 경우에는
inode를 가리킵니다. file 구조체 안에는 또 readable 플래그와 writable 플래그 두 개가 있어서,

그 파일을 읽을 수 있는지, 쓸 수 있는지, 아니면 둘 다 가능한지를 나타냅니다. 파이프의 경우에는 file 구조체가 두 개 있습니다. 하나는 읽기 끝(read end)을 위한
것이고, 하나는 쓰기 끝(write end)을 위한 것입니다. 읽기 끝에 대한 file 구조체라면, 타입은 FD_PIPE가 될 것이고, readable 플래그는
참(true)이지만,

파이프의 왼쪽 끝을 위한 파일은 읽기 가능하지만 쓰기 불가능하게 표시될 것이고, 파이프의 오른쪽 끝 파일을 위한 파일 구조체도 다시 하나 있으며, 이번엔 쓰기 가능하지만 읽기
불가능하게 표시될 것입니다. 그래서 파이프를 가리키는 포인터 두 개와, 파이프의 각 끝을 위한 파일 구조체 두 개를 갖게 됩니다. 이 파일 구조체들에는 참조 카운트도 들어
있습니다. 여기엔 그려 놓지 않았지만요.

파일 구조체는 여러 다른 프로세스들에 의해 가리켜질 수 있습니다. 특정한 하나의 파일이 많은 다른 프로세스들에 의해 open될 수 있기 때문입니다. 그래서 여기 여러 개의 다른
포인터들이 있고, 참조 카운트는 그 개수를 추적합니다. 그리고 그 값이 0이 되면, 그 파일 구조체가 사용하던 공간을 회수해서 free pool에 다시 돌려줄 수 있습니다.

반면에 파이프 구조체는 정확히 두 개의 포인터만이 그것을 가리키게 됩니다. 그래서 파이프 구조체 안에는 아까 보여줬던 두 필드, readopen 플래그와 writeopen 플래그가
있습니다. readopen 플래그는, 그리고 오직 그때만, 이 파이프 구조체를 가리키는 파일 객체가 있을 때 true가 됩니다. 마찬가지로 writeopen 플래그는, 그리고 오직
그때만, 이 파이프 구조체를 가리키는 오른쪽 끝 파일이 있을 때 true가 됩니다.

그리고 readopen과 writeopen이 둘 다 false라면, 이 파이프 객체를 가리키는 포인터가 하나도 없다고 말할 수 있고, 그러면 이 객체를 반환할 수 있습니다. 그
경우에는 이 파이프가 올라가 있는 페이지 전체를 Kfree 함수를 호출해서 해제하게 됩니다. 자, 이제 하고 싶은 것은 이 프로세스 P가 pipe 시스템 콜을 호출해서 파이프를
만들고, 두 개의 파일 객체를 할당하고, 이 포인터들을 설정했다고 가정하는 것입니다.

그래서 pipe 시스템 콜 후의 상황이 여기 보이는 모습입니다. 시스템 콜은 파일 디스크립터 배열에서 비어 있는 슬롯을 찾아서 그것들을 사용하고, 그 번호들을 사용자 모드
프로세스에 반환합니다. 이 경우에는 2와 4를 반환해서, 사용자 프로세스가 읽기 끝이나 쓰기 끝을 가리킬 수 있게 합니다.

이제 이 프로세스가 자식 둘을 fork한다고 가정해 봅시다. 한 자식은 reader 프로세스가 되고, 다른 자식은 writer 프로세스가 될 겁니다. 프로세스를 fork할 때마다
이 배열을 통째로 복사합니다. 즉, 열려 있는 모든 파일들을 그대로 복사합니다. 부모에서 어떤 파일이 열려 있었다면, 자식에서도 그 파일은 열려 있게 됩니다. 그래서 초기에는 여기
포인터 2와 포인터 4가 둘 다 이 두 파일 객체를 가리키도록 설정됩니다.

하지만 reader 프로세스가 곧바로 쓰기 끝을 close한다고 가정하겠습니다. 그러면 이 객체에 대한 참조 카운트를 감소시키고, 이 포인터를 0으로 설정합니다. 더 이상 그
포인터가 존재하지 않기 때문입니다. 그리고 프로세스 P는 writer 프로세스도 fork할 것이고, 다시 전체 ofile 배열이 복사되고, 모든 파일 객체들의 참조 카운트가
증가합니다.

그다음에 프로세스 W가 곧바로 읽기 끝을 close한다고 가정하겠습니다. 그러면 이 포인터를 따라가서 참조 카운트를 감소시키고, 그것을 null로 설정하게 됩니다. 그래서 이제
이런 상황이 됩니다. 참고로 제 인덱스가 그림에서 딱 맞게 정렬되지는 않았지만, 무슨 뜻인지는 아실 거라 생각합니다. 이 시점에서의 상황은 다음과 같습니다.

프로세스 R은 파이프의 읽기 끝에 대한 파일 객체를 가리키고, 프로세스 W는 파이프의 쓰기 끝에 대한 파일 객체를 가리키고 있습니다. 부모 프로세스는 여전히 이 포인터들을 가지고
있고, 아마 그것들을 close할 수도 있고 안 할 수도 있습니다. 어떻게 할지는 모릅니다. 어쨌든 이 시점에서 프로세스 W는 파일 디스크립터 4에 대해 write 시스템 콜을

한편 reader는 파일 디스크립터 2를 사용해서 read 시스템 콜을 실행함으로써 파이프로부터 데이터를 읽을 수 있습니다.

것인지에 대한 주소를 넘깁니다. 즉, 여기 인자로 들어온 가상 주소에 지금까지 읽은 바이트 수만큼 오프셋을 더한 주소입니다. 그리고 방금 가져온 바이트에 대한 포인터와 바이트 수
1을 함께 넘깁니다. 이게 잘 작동하면 루프 처음으로 돌아가고, 그렇지 않으면 루프를 빠져나와 작업을 끝냅니다.

어쨌든 우리가 바이트를 읽었습니다. 사실은 아무 바이트도 가져오지 못해서 in read를 증가시키지 않았을 수도 있지만, 프로세스를 깨우는 것은 해가 되지 않습니다. 어떤 경우든,
아마도 파이프에서 몇 바이트를 제거했을 것이므로, 반드시 writer들을 깨워야 합니다. 이제 파이프는 더 이상 꽉 차 있지 않을 수 있기 때문입니다.

그래서 writer에게는 write 인덱스의 주소를 채널로 사용합니다. 즉, reader들은 read 인덱스를 채널로 삼아 잠들고 write 인덱스를 채널로 삼아 깨어나고,
writer들은 write 인덱스를 채널로 삼아 잠들고 read 인덱스를 채널로 삼아 깨어납니다. 모든 대기 중인 writer들을 깨운 다음에는 스핀락을 해제하고, 여기 줄에서
사용자 가상 주소 공간으로 옮긴 바이트 수를 반환합니다.

이제 다음으로 write 함수로 넘어가겠습니다. 이것이 pipe write 함수입니다. pipe read 함수와 마찬가지로, pipe 구조체에 대한 포인터와 주소, 바이트 수를
인자로 받습니다. 주소는 사용자 주소 공간의 가상 주소이고, n은 그 가상 주소 공간에서 파이프로 옮길 바이트 수입니다. 이 함수는 파이프로 옮긴 바이트 수를 반환합니다.

pipe read의 경우, 반환값은 요청한 바이트 수보다 작을 수 있습니다. pipe read 함수는 최소한 한 바이트라도 읽으려고 시도하지만, 파이프에 더 이상 대기 중인
데이터가 없으면 한 바이트를 읽은 뒤 곧바로 반환합니다. 반면에 pipe write는 n 바이트 전부를 쓰려고 시도하며, 보통은 n을 반환합니다. 어떤 오류가 있으면 -1을 반환할
수 있고, 페이지 테이블에 문제가 있으면 n보다 작은 값을 반환할 수도 있지만, 정상적인 경우에는 n 바이트 전부를 반환합니다.

이 함수의 구조는 루프이며, 루프의 각 반복에서 정확히 한 바이트를 옮기려고 시도합니다. 그 작업이 바로 여기에서 일어나고, 우리는 i를 증가시킵니다. i는 처음에는 0에서
시작하며, 지금까지 옮긴 바이트 수를 나타냅니다. 계속 증가하다가, 루프를 빠져나올 시점에는 i가 n과 같아지고, 옮긴 바이트 수인 n을 반환합니다. 페이지 테이블에 문제가
있다면, 루프를 일찍 빠져나와서 n보다 작은 값을 반환할 수 있습니다.

이제 세부 내용을 보겠습니다. 먼저 루프 몸체에서 reader가 존재하는지 검사합니다.

파이프 구조체의 read open 플래그가 false라면, 즉 읽는 쪽이 하나도 없다면 곧바로 -1을 리턴합니다. 마찬가지로 이 프로세스가 kill된 경우에는, 이 프로세스의
killed 필드가 설정될 것이고, 즉시 중단하고 -1을 리턴해야 합니다. 하지만 어느 경우든 리턴하기 전에 먼저 스핀락을 해제합니다.

모든 것이 괜찮다고 가정하면, 다음으로 파이프가 가득 찼는지 확인해야 합니다.

여기 그 검사 코드가 있습니다. read 더하기 파이프 크기(512)가 write 인덱스와 같다면, 파이프가 가득 찬 상황입니다. 여기 그림에서 보이듯이, in->read +
512 가 in->write 와 같을 때입니다. 파이프가 가득 찬 경우라면 잠자기(sleep) 상태로 들어가야 합니다. 그리고 sleep 함수의 채널(channel)로는 파이프
구조체 안의 write 인덱스의 주소를 사용합니다.

그리고 읽는 쪽 프로세스들은 바로 그 채널을 사용해서 wakeup 될 것입니다. 이게 파이프 read 함수인데, 기억하듯이 wakeup 할 때는, 깨우고 싶은 파이프의 write
인덱스를 채널로 사용해서 wakeup을 합니다. 다만 우리가 잠자기에 들어가기 전에, 어딘가에 잠들어 있는 reader 들이 있을 수 있으므로, 잠들어 있는 reader 들을
깨워야 합니다.

이 루프가 여러 번 돈 상황일 수 있습니다. 처음에는 빈 파이프에서 시작했을 수도 있고, reader 들이 깨어나기를 기다리며 잠들어 있었을 수도 있습니다. 그리고 n 값이
512보다 매우 큰 값일 수 있고, 이 루프를 충분히 많이 실행해서 파이프를 가득 채웠을 수 있습니다. 그런 경우 파이프가 가득 찼으니 우리는 잠자기에 들어가야 하지만, 파이프가
비어 있었을 때 잠들었던 reader 들이 있으므로, 우리가 잠들기 전에 그 reader 들을 먼저 깨워야 합니다.

파이프가 가득 차지 않았다고 가정하면, 이제 바이트를 파이프로 옮길 수 있습니다. 여기서 일어나는 일이 바로 그것입니다. copyin 함수를 이용해, 여기 주어진 페이지 테이블이
묘사하는 가상 주소 공간에서 바이트를 복사해 와서, 지역 변수 ch에 저장합니다.

어디에서 복사하느냐 하면, 가상 주소 + 이미 복사한 바이트 수 만큼을 더한 위치에서, 한 번에 1바이트씩 복사합니다. 만약 복사 도중 어떤 문제가 생기면, 지금까지 성공적으로
복사한 바이트 수만큼을 가지고 pipe write 함수를 중단합니다. 이 루프를 빠져나가고, 지금까지 복사한 바이트 수를 리턴합니다.

하지만 모든 것이 정상이라면, 사용자 가상 주소 공간에서 한 바이트를 가져온 것이고, 다음 줄에서 그 바이트를 이 파이프의 버퍼에 집어넣습니다. write 인덱스를 사용하고, 이를
파이프 크기 512로 나눈 나머지 위치를 버퍼 인덱스로 사용해서, 그 위치에 바이트를 저장합니다. 그리고 write 인덱스를 증가시키고, i도 증가시킨 다음 루프 처음으로
돌아갑니다.

파이프에 데이터를 채우고 난 뒤에는, 잠들어 있던 reader 들이 있었을 수 있으므로 wakeup을 호출해야 합니다. 다시, 채널로는 이 파이프의 in->read 인덱스의 주소를
사용합니다. 이게 이 파이프에서 잠든 어떤 프로세스든 잠들어 있던 채널입니다. 마지막으로 이 파이프에 대한 스핀락을 해제하고, 지금까지 전송한 바이트 수를 리턴합니다.

마지막으로 pipeclose 함수를 살펴보겠습니다. 가끔 사용자 프로세스가 close 시스템 콜을 호출하면서, 예를 들면 파일 디스크립터 번호 2 같은 값을 넘깁니다. 이것의
의미는, 사용자가 이 포인터를 제거해서, 이 프로세스에서 이 파일을 없애고 싶다는 뜻입니다. 각 file 객체에는 참조 카운트가 붙어 있고, 이 포인터를 제거했을 때 참조 카운트가
0이 되지 않으면 아무 일도 하지 않습니다.

하지만 결국에는 더 이상 그 file 객체를 가리키는 포인터가 하나도 없게 되면 참조 카운트가 0이 될 것이고, 그 시점에는 이 file 객체를 free pool로 되돌려야 하고,
여기 있는 포인터도 제거해야 합니다. 그 시점에 바로 이 객체에 대해 pipeclose 함수를 호출하게 됩니다. 읽기 끝을 닫든, 쓰기 끝을 닫든, 언제든지 끝을 닫을 때는 이
pipeclose 함수가 호출됩니다. 이제 이것을 살펴보겠습니다.

이 함수는 파이프 구조체에 대한 포인터 하나와, 쓰기 끝을 닫는지 읽기 끝을 닫는지를 나타내는 플래그를 인자로 받습니다. 그게 여기 인자입니다. 먼저 이 파이프 객체에 대한 락을
획득합니다. 그리고 만약 쓰기 끝을 닫는 경우라면, 파이프 구조체의 write open 플래그를 0으로 설정합니다. 바로 여기 있는 필드를 0으로 만들어, 쓰기 끝에 해당하는
file 객체에서 포인터를 잃어버렸다는 것을 표시합니다.

이때, 파이프를 읽고 있는 프로세스들이 있을 수 있고, 파이프가 비어 있는 것을 발견해서 기다리느라 잠들어 있을 수도 있습니다. 이들은 파이프에 뭔가가 들어오기만을 기다리고 있는
상황이므로, 이들을 깨워야 합니다. reader 는 파이프가 비어 있다고 판단하면 잠들게 된다는 점을 기억하십시오.

다시 pipe read로 가보면, 파이프가 비어 있으면 잠들지만, 동시에 writer가 있는지도 확인합니다. 만약 우리가 쓰기 끝을 제거해서, 쓰기 끝을 닫으면, 여기 잠든
reader를 깨워야 합니다. reader 는 깨어난 뒤 다시 상태를 확인하고, 이제는 write end 가 열려 있지 않다는 것을 알게 되고, 0을 리턴하게 됩니다. 여기서
일어나는 일이 바로 그것입니다. 우리가 쓰기 끝을 닫으면, 플래그를 0으로 설정해 이제 쓰기 끝이 없다는 것을 표시하고, 기다리던 reader 들을 깨웁니다.

반대로 읽기 끝을 닫는다면, read open 플래그를 0으로 설정하고, 같은 이유로 잠들어 있던 writer 들을 깨웁니다.

마지막으로, 읽기 끝과 쓰기 끝 둘 다 닫아버린 경우, 즉 이제 두 플래그가 모두 0이 되었다면, 이 파이프 객체 전체가 더 이상 필요 없다는 뜻입니다. 그 시점에는 락을
해제하고, 이 파이프 객체가 들어 있던 페이지를 kfree를 호출해 페이지 free pool로 되돌려 보냅니다. 아직 어느 한쪽 끝이라도 열려 있다면, 단지 이 파이프 객체의
스핀락만 해제하고 리턴합니다.
