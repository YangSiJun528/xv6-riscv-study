포인터가 어떤 file 구조체를 가리킨 상태로 넘어오면, 이 함수가 제일 먼저 하는 일은 참조 카운트를 감소시키는 일입니다. 그래서 먼저 100개의 file 구조체 테이블에 대한

하지만 이 file 구조체가 우리가 따로 처리해야 하는 다른 구조체들을 가리키고 있을 수 있습니다.

그래서 여기에서, 우리가 전에 살펴본 pipe_close를 호출합니다. 이게 읽기 끝인지 쓰기 끝인지는, writable 플래그의 값을 넘겨줌으로써 결정합니다. 반면 type이

file.c 파일에는 함수가 세 개 더 있습니다. file_stat, file_read, 그리고 file_write 함수가 있습니다. 이 비디오의 나머지 부분에서는
file_stat만 이야기하고, 나머지는 이후 비디오에서 다루겠습니다. file_stat은 fstat 시스템 콜에 사용됩니다. fstat 시스템 콜이 무엇을 하는지 간단히 복습해
봅시다. 이 시스템 콜은 Unix와 xv6 둘 다에서 제공되고, 정의도 거의 같습니다. 작은 정수 하나를 넘겨받는데, 이것이 어떤 파일에 대해 알고 싶은지를 나타냅니다.

또한 사용자 가상 주소 공간 어딘가를 가리키는 포인터도 함께 넘겨받습니다. 이 시스템 콜이 하는 일은, 그 사용자 가상 주소 공간으로 해당 파일에 대한 여러 정보를 옮겨 넣는

0을, 오류가 있으면 -1을 반환합니다.

Unix에서는 errno 변수라는 것이 있으며, 커널이 오류가 있을 경우 무엇이 원인이었는지를 나타내기 위해 이 값도 설정합니다. 하지만 xv6에서는 errno를 건드리지
않습니다. 그런 오류 번호 시스템을 쓰지 않으므로 전혀 사용하지 않습니다. 자, 시스템 콜이 일어나면 커널은 사용자 프로그램으로부터 제어권을 넘겨받고, 어느 시스템 콜인지를
알아내기 위해 레지스터를 살펴본 뒤, 실제 일을 하는 이 sys 함수들 중 하나를 호출합니다. fstat 시스템 콜의 경우, 커널은 sys_fstat을 호출하는데, 이 함수는
file/sysfile.c 안에 있습니다. 이 함수들은 인자를 받지 않고, 사용자 코드로 돌려보낼 반환값을 리턴합니다. 그러니까 여기서는 0 또는 -1을 리턴하게 됩니다.

그럼 이 함수가 실제로 무엇을 하느냐 하면, 우선 사용자 코드가 넘기려 했던 인자들을 얻어와야 합니다. 인자들은 레지스터로 넘겨지고, 그 레지스터 값들은 저장되어 있으므로,
argint, argaddr 같은 함수를 호출해야 합니다. 이 함수들은 예전에 제가 만든 비디오에서 다룬 적이 있습니다. 이 함수들이 하는 일은, 우리가 가져오고 싶은 인자의
번호를 넘겨받는 것입니다.

여기에서는 첫 번째 인자(번호 0)와 두 번째 인자(번호 1)를 가져옵니다. argaddr의 경우 그 인자는 가상 주소가 되며, 그 값을 어디에 저장할지 주소를 넘겨 줍니다.
그래서 이 변수는 지역 변수이고, argaddr 함수는 저장된 레지스터를 찾아서 그 값을 여기 st 위치에 복사합니다. 문제가 있으면 -1을 리턴하고, 그러면 우리는 즉시 -1을
리턴합니다.

argfd 함수는 아직 보지 않았지만, 비슷한 종류의 함수입니다. 마찬가지로 가져오고 싶은 인자의 번호(레지스터 번호가 아니라 “인자 번호”)와 그 값을 저장할 위치를 넘겨줍니다.
이 값은 file descriptor이므로, f의 주소를 넘겨줍니다. 그러면 이 함수는 이 파일에 대한 file 구조체 포인터를 얻어옵니다.

그래서 argfd를 잠깐 살펴보겠습니다. 주석은 다음과 같은 일을 설명합니다. “n번째 시스템 콜 인자를 file descriptor로서 가져오고, file descriptor와
해당 file 구조체 포인터 둘 다를 반환한다.” 따라서 인자 번호를 넘겨받고, 포인터 두 개를 인자로 받습니다. 하나는 file descriptor(작은 정수)를 저장할
위치이고, 다른 하나는 file 구조체 포인터를 저장할 위치입니다.

먼저 argint를 호출하면서 인자 번호 n을 넘겨주고, 그 결과를 이 지역 변수 fd에 저장합니다. 여기에 문제가 있으면 -1을 리턴합니다. 그다음 방금 얻어온 이 file
descriptor가 유효한지 검사합니다. 0 이상인지, 그리고 우리가 가진 최대 열린 파일 개수보다 크지 않은지를 확인합니다. 그리고 o_file 배열을 살펴보면서 널 포인터인지
아닌지도 확인합니다.

즉, 현재 프로세스의 proc 구조체로 가서, 그 안의 open file 배열을 들여다봅니다. 제 그림에서는 이것이 어떤 프로시저의 proc 구조체이고, 여기서 ofile 배열을
보고 있는 상황입니다. 인덱스가 0보다 작지 않고, 이 배열의 엔트리 개수(즉 ofile의 길이)보다 크지 않은지 확인합니다. 그리고 그 엔트리 값이 널 포인터가 아닌지도
확인합니다. 조건이 맞으면 그 엔트리를 따라가서 file 구조체에 대한 포인터를 얻고, 그 포인터를 리턴합니다. 요약하자면, 범위 안에 있는지, 널이 아닌지를 확인한 뒤, file
구조체 포인터를 꺼내오는 것입니다.

파일 디스크립터 자체를 저장하고 싶다면, 이 인자는 그 파일 디스크립터(작은 정수)를 어디에 저장할지 가리키는 포인터가 됩니다. 그렇지 않다면 null 이겠죠. 그래서 이 인자가
null 이면 아무것도 하지 않고, 포인터라면 그 포인터가 가리키는 곳에 파일 디스크립터를 저장합니다.

그리고 이 인자는 파일 구조체를 어디에 저장할지 가리키는 포인터가 됩니다. 이것도 null 이면 아무것도 하지 않고, 포인터라면 그 포인터가 가리키는 곳에 파일 구조체에 대한
포인터를 저장합니다. 그리고 0을 반환합니다.

이제 다시 시스템 콜 쪽으로 돌아갈 준비가 되었습니다. 우리는 파일 구조체에 대한 포인터를 가지고 있습니다. 실제 파일 디스크립터 번호에는 관심이 없어서 따로 저장하지 않았습니다.
만약 문제가 있었다면 -1을 반환했을 것이고요. 이제 실제 일을 하도록 filestat를 호출합니다. 파일 구조체에 대한 포인터와, stat 구조체의 가상 주소 st 를 인자로
넘깁니다.

이제 다시 file.c 로 돌아왔고, 여기 file stat 함수가 있습니다. 현재 프로세스에 대한 포인터를 얻고, 그다음 이 파일 구조체 f 를 살펴봅니다. 이게 inode
인가, 아니면 디바이스인가를 보는 거죠. 만약 그렇다면 ip 포인터가 유효할 것이고, 그래서 뭔가를 반환할 수 있습니다. 하지만 pipe 라면 문제가 있으므로 -1을 반환합니다.
따라서 ip 가 inode 를 가리키고 있다는 것은 타입이 inode 이거나 device 라는 뜻이고, 즉 일반 파일이거나 디렉터리 파일이거나, 아니면 디바이스라는 뜻입니다. 어느

그래서 우리가 할 일은, 이 포인터가 가리키는 inode 를 lock 한 다음, 조금 전에 이야기했던 stati 함수를 사용하는 것입니다. 이 함수가 inode 에서 데이터를
복사해서 이 가상 주소에 있는, 가상 주소 공간으로 옮깁니다.

정확히 말하면, 먼저 커널 공간으로 복사합니다. 여기 커널 공간 안에 우리가 데이터를 저장할 변수 하나가 있고, 거기에 데이터를 채운 다음 inode 의 lock 을 해제합니다.
그리고 여기에서 커널 안에 있는 그 데이터를 가상 주소 공간으로 복사합니다. xv6 가 하는 일 중 하나는 이런 식의 복사를 상당히 많이 한다는 점입니다. 없앨 수도 있을 것 같은
복사들이죠. 설계를 다르게 했다면, 바로 가상 주소 공간으로 직접 복사할 수도 있었을지 모릅니다. 하지만 어쨌든 현재 설계에서는, 먼저 stati 를 써서 이 stat 구조체로 한
번 복사하고, 다시 copyout 을 사용해서 가상 주소 공간으로 복사합니다.

즉, 이 페이지 테이블이 기술하는 가상 주소 공간으로 복사하는 것이고, 여기 우리가 복사할 목적지 가상 주소가 있습니다. 그리고 여기 복사 출발지가 있는데, 바로 이 지역 변수
st 입니다. 그리고 이 구조체가 차지하는 바이트 수만큼을 복사합니다. 만약 문제가 생기면 -1 을 반환하고, 그렇지 않으면 0을 반환해서 모든 것이 잘 끝났음을 알립니다.
