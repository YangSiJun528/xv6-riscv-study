## 한국어 번역

이 비디오는 xv6 운영체제 커널에 대한 시리즈의 일부입니다. 이 비디오에서는 주소 변환(address translation)에 대해 이야기하고, xv6 커널을 이해하는 데 필요한
범위에서 RISC-V 프로세서에서 사용되는 페이지 테이블 구조(page table architecture)를 설명하겠습니다. 여기서 알아야 할 레지스터는 satp, 즉 주소 변환
포인터용 Supervisor 레지스터입니다.

satp는 제어/상태 레지스터이고, 페이지 테이블을 가리키도록 설정됩니다. 페이지 테이블은 주기억장치에 위치하며, 항상 한 시점에는 딱 하나의 페이지 테이블만 사용 중인데, 그
페이지 테이블을 satp 레지스터가 가리키게 됩니다. RISC-V 코어에서의 가상 주소 변환은, 초기화가 끝난 뒤에는 항상 켜져 있습니다. 처음에는 satp가 0이고, satp가
0일 때는 주소 변환이 일어나지 않습니다. 하지만 초기화 과정에서 우리가 사용하고자 하는 페이지 테이블을 가리키도록 satp를 설정합니다. Supervisor 모드와 User
모드에서 실행할 때는 항상 주소 변환이 켜져 있고, Machine 모드에서는 켜져 있지 않습니다.

페이지 테이블은 여러 개가 있습니다. 먼저 커널용 페이지 테이블이 하나 있고, 모든 코어는 이 커널용 페이지 테이블을 공유합니다. 이 커널 페이지 테이블은 거의 1:1 매핑을
제공합니다. 몇 가지 예외는 있지만, 물리 메모리 전체를 매핑해서, 커널 코드가 메모리의 어떤 위치든지 주소 계산 같은 것을 따로 하지 않고 바로 접근할 수 있게 해 줍니다. 또한
여러 메모리 매핑 I/O 장치들도 있는데, 커널의 페이지 테이블은 이 장치들도 직접 매핑합니다. 이 하나의 커널 페이지 테이블 외에, 각 사용자 모드 프로세스마다 별도의 페이지
테이블이 하나씩 있습니다.

RISC-V에는 페이지 테이블을 구현하는 여러 옵션이 있습니다. 이 옵션들을 sv32, sv39, sv48이라고 부릅니다. sv32는 2단계 구현 방식, sv39는 3단계 구조,
sv48은 4단계 구조입니다. sv32는 32비트 프로세서에서 사용할 수 있습니다. 우리는 64비트 프로세서만 신경 쓰면 되고, xv6는 sv39 방식을 사용합니다. 따라서
프로세서는 sv39 방식을 구현하고 있고, 3단계(page table) 구조를 갖습니다. 다른 옵션들도 있지만 여기서는 다루지 않겠습니다.

주기억장치로의 모든 load, store, 그리고 명령어 fetch는 개념적으로는 항상 페이지 테이블을 따라가서(page table walk) 주소 변환을 찾습니다. 즉, 페이지
테이블을 차례대로 지나가며 사용할 주소 변환을 찾는 것입니다. 하지만 이 페이지 테이블 워크는 여러 번의 메모리 접근을 필요로 하고, 그대로 하면 엄청나게 비효율적입니다. 따라서
성능을 위해 실제 프로세서에는 TLB(translation lookaside buffer)라는 것이 있습니다. TLB는 코어 안에 있는 레지스터들이고, 보통은 프로그래머에게는
투명, 즉 보이지 않는 존재입니다.

이 레지스터들은 기본적으로 최근에 사용한 페이지 테이블 엔트리들을 캐시처럼 저장합니다. 커널 프로그래머 입장에서 알아야 할 것은, 페이지 테이블을 바꿀 때마다, 즉 satp
레지스터를 갱신할 때마다 캐시를 비워야 한다는 점입니다. 모든 TLB를 비워야 합니다. 이를 위해 RISC-V 명령어 집합에는 sfence.vma라는 명령이 있습니다. 커널에는
sfence.vma라는 이름의 함수가 있고, 이 함수는 사실상 이 명령어를 한 번 실행하는 것 말고는 별다른 일을 하지 않습니다.

이제 sv39 방식에서의 가상 주소를 살펴보겠습니다. sv39에서 가상 주소는 39비트입니다. 이 주소는 먼저 오프셋(offset)과 나머지로 나눌 수 있습니다. 모든 페이지는
4킬로바이트 크기이고, 2의 12승이 4KB이므로, 페이지 내부에서 위치를 지정하려면 정확히 12비트가 필요합니다. 나머지 27비트는 세 개의 필드로 나뉘어서, 페이지 테이블의
레벨 2, 레벨 1, 레벨 0을 인덱싱하는 데 사용됩니다. 이 위쪽 비트들은 무시됩니다.

페이지 테이블을 접근하면 페이지 테이블 엔트리(page table entry)를 얻게 되는데, 이 엔트리에는 이 접근을 허용할지 말지를 제어하는 여러 비트가 들어 있습니다. r
비트가 설정되어 있으면 읽기가 허용됩니다. w 비트가 설정되어 있으면 쓰기가 허용됩니다. x 비트는 실행 가능(executable) 여부를 나타냅니다. 또한 u 비트가 있어서, 이
페이지가 사용자 모드에서 접근 가능한지, 아니면 Supervisor 모드에서만 접근 가능한지를 나타냅니다. 마지막으로 v 비트가 있는데, valid를 의미하며 이 페이지 테이블
엔트리가 유효한지 여부를 나타냅니다. 이 밖에도 몇 가지 비트가 더 있지만, 우리는 그것들에는 신경 쓰지 않겠습니다.

엔트리에는 물리 페이지 번호(physical page number)도 들어 있습니다. 주소 변환 하드웨어는 가상 주소로부터 이 인덱스 비트들을 사용해서 올바른 엔트리를 찾아 페이지
테이블 엔트리를 읽어온 다음, 페이지 번호의 44비트와 오프셋의 12비트를 합쳐서 물리 주소를 만듭니다. 결과 물리 주소는 56비트가 됩니다. 따라서 이 구조로는 최대 2의 56승
바이트의 물리 메모리를 지원할 수 있습니다.

이제 페이지 테이블 자체를 보겠습니다. 앞에서 봤듯이 인덱스 필드는 세 개이고, 각 필드는 9비트입니다. 페이지 테이블 구조는 다음과 같습니다. 여기 satp 레지스터가 있고,
satp는 어떤 트리를 가리킵니다. 이 트리의 각 노드는 주기억장치에 있는 4KB 페이지 하나이고, 트리는 3단계의 레벨을 가집니다. 맨 아래 리프(leaf) 레벨에는 실제 데이터
페이지들이 있습니다. 트리 안의 모든 노드와 리프는 4KB짜리 페이지입니다.

페이지 테이블의 각 내부 노드, 즉 페이지 테이블의 각 레벨에 있는 페이지는 512개의 엔트리를 포함합니다. 각 엔트리는 64비트이고, 64비트는 8바이트입니다. 8바이트에
512개를 곱하면 4096바이트가 되어, 딱 4KB가 됩니다. 따라서 각 노드에는 512개의 엔트리가 들어갈 수 있고, 각 엔트리는 페이지 테이블 엔트리이며, 여러 비트와 함께
다음 레벨 노드를 가리키는 포인터를 포함합니다.

동작 방식은 다음과 같습니다. 하드웨어는 먼저 여기 첫 번째 9비트 필드를 보고, 이를 루트 노드를 인덱싱하기 위한 값으로 사용합니다. 2의 9승은 512이므로, 9비트면 정확히
512개 엔트리 중 하나를 고를 수 있습니다. 물론 12비트 오프셋은 데이터 페이지 안에서 어떤 바이트든 접근할 수 있게 해 줍니다. 2의 12승은 4096이기 때문입니다.

그래서 먼저 레벨 2 인덱스를 사용해 루트 노드에서 하나의 엔트리를 읽고, 그 엔트리에 들어 있는 포인터를 얻습니다. 다음 9비트 인덱스를 사용해 그 다음 레벨 노드를
인덱싱합니다. 거기서 또 포인터를 얻고, 마지막 인덱스를 사용해 마지막 레벨 페이지를 인덱싱합니다. 이렇게 해서 최종 페이지 테이블 엔트리를 얻게 되고, 이 엔트리가 여기 표시된
것처럼 데이터 페이지에 대한 접근 권한을 검사하는 데 사용되고, 동시에 물리 주소를 구성하는 데 사용됩니다.

페이지 테이블 구조 설명은 여기까지입니다. 다음 비디오에서 다시 보겠습니다.
