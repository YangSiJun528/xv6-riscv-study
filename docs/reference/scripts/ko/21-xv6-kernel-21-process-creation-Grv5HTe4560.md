## 한국어 번역

이 비디오는 xv6 운영체제 커널에 대한 연속 강의 중 하나이고, 이 비디오에서는 프로세스, 특히 프로세스를 표현하기 위해 사용되는 자료구조에 대해 이야기하겠습니다. proc
구조체 배열이 어떻게 초기화되는지, 그리고 초기 첫 번째 프로세스를 위해 데이터를 어떻게 설정하는지를 다룰 겁니다. 이 내용은 모두 파일 proc.c 에서 가져온 것이고, 그
파일에는 이 외에도 여러 가지 다른 내용이 들어 있습니다.

제가 지금 설명할 내용 외에도, 그 파일에는 스케줄러, yield 같은 것들의 코드와 sleep, wakeup 함수의 코드도 들어 있습니다. 이런 것들은 이전 비디오들에서 이미
다뤘습니다. 또 fork, wait, kill 같은 함수들의 코드도 들어 있는데, 이들은 앞으로의 비디오에서 다룰 예정입니다. 자, 이제 파일 자체부터 시작해 보겠습니다.

먼저 이 두 필드를 보고 싶습니다. 하나는 1로 초기화된 프로세스 id 카운터이고, 다른 하나는 pid_lock 이라는 스핀락입니다. 그러니 바로 이 allocpid 함수부터
살펴볼 수 있습니다. 새로운 프로세스 id가 필요할 때마다 이 함수를 호출할 수 있고, 동작은 꽤 단순합니다. 새 프로세스 id를 반환하는데, 전역 변수 nextpid 를 읽고
갱신하기 위해서는 먼저 락을 획득해야 합니다. 여기서 락을 획득하고, 현재 값을 로컬 변수에 읽어온 뒤 전역 변수를 증가시키고, 마지막에 락을 해제합니다. acquire 와
release 를 사용하는 아주 단순한 예입니다. 이 부분을 정리했으니, 이제 제가 다루고 싶은 첫 번째 함수로 들어가겠습니다.

그 함수는 procinit 입니다. 그 전에, 이 비디오와 관련된 구조체들을 다시 한 번 상기시키겠습니다. proc 구조체의 배열이 있고, 여기에는 그 중 하나만 그려져 있지만,
전체적으로 64개가 있습니다. 각 프로세스마다 하나씩입니다. 그리고 각 proc 구조체 안에는 스핀락과 몇 개의 필드가 있는데, 예를 들어 상태(state) — running 인지
runnable 인지 등 — 가 있고, channel(잠들어 있을 때 사용하는 값), 프로세스가 kill 되었는지 여부를 나타내는 불리언 값과 그 밖의 여러 필드들이 있습니다. 또
가상 메모리 안에서 스택이 위치하는 영역을 가리키는 포인터도 있습니다. 이 부분은 잠시 후에 다시 이야기하겠습니다. 해당 프로세스의 주소 공간 크기, 즉 힙의 꼭대기(브레이크
포인트)를 나타내는 값, 페이지 테이블을 가리키는 포인터, trapframe 을 가리키는 포인터, 컨텍스트를 저장하기 위한 context, 그리고 그 밖의 몇 가지 다른 것들(예를
들어 name 필드)이 있습니다.

지금은 그것들을 모두 자세히 다루지는 않고, 우선 procinit 함수에 대해 이야기하고 싶습니다. 이 함수는 처음에 proc 배열을 초기화합니다. 커널 초기화 과정에서 코어 0에
의해 단 한 번만 호출됩니다. 그리고 방금 본 프로세스 id용 락을 초기화하고, wait_lock 이라는 또 다른 락도 초기화합니다.

그 다음에 proc 배열을 순회합니다. 즉, 이 proc 배열을 쭉 돌면서, 각 원소마다 스핀락을 초기화합니다. 배열을 지나가면서 각 항목마다 스핀락을 초기화하고, 동시에
kstack 도 초기화합니다. 이 시점에서 커널의 가상 주소 공간이 어떻게 생겼는지 이야기하겠습니다.

커널의 가상 주소 공간은, 다른 주소 공간들과 마찬가지로, 가장 위쪽 페이지에 trampoline 페이지가 매핑되어 있고, 그 아래에 guard 페이지들과 스택 페이지들이 연속해서
있습니다. 64개 프로세스 각각에 대해, 그 프로세스가 커널 모드로 실행될 때 사용할 스택을 위한 페이지가 가상 주소 공간 안에 한 페이지씩 존재합니다.

procinit 함수의 이 지점에서, 우리는 그 스택 페이지의 가상 주소를 결정하고 있습니다. 이것은 전처리기 매크로 함수로, 0에서 63 사이의 숫자를 받아서 그 스택 페이지의
가상 주소를 계산해 줍니다. 그리고 계산된 값을 그 proc 구조체의 kstack 필드에 저장합니다. 여기 proc 구조체가 다시 보이고, 여기 kstack 필드가 있습니다.
여기에 단순히 가상 주소를 저장합니다. 제가 점선으로 표시해 둔 것은 이것이 가상 주소라는 것을 나타내기 위한 것이고, 반면 여기 있는 링크들 — 예를 들어 page table
포인터는 물리 메모리 어딘가의 물리 주소를 가리키고, trapframe 포인터도 trapframe 의 실제 물리 주소를 가리킵니다. trapframe 은 물론 가상 주소 공간의
위에서 두 번째 페이지에 매핑되지만, 이 포인터 자체는 kalloc 이 반환한 실제 물리 페이지를 가리킵니다. 그것이 어떻게 되는지는 곧 보겠습니다.

이 파일 안에는 제가 이미 언급한 몇 가지 다른 함수들도 있는데, 잠깐만 다시 짚고 넘어가겠습니다. cpuid 는 현재 이 함수를 실행 중인 코어 번호를 tp 레지스터의 값을
반환함으로써 얻습니다. mycpu 는 그 현재 코어 번호를 이용해 해당 CPU struct 에 대한 포인터를 반환합니다.

여기 CPU struct 들의 배열이 있고, 그 중 하나만 그려져 있습니다. 최대 8개의 코어가 있고(상수로 정해져 있습니다), 각 코어마다 하나의 CPU 구조체가 있습니다.
우리는 현재 코어에 해당하는 CPU 구조체의 포인터를 반환합니다. 마지막으로 myproc 루틴이 있는데, 이 루틴은 현재 CPU struct 의 포인터를 얻은 다음, 그 안의
proc 필드를 따라가서 현재 실행 중인 프로세스를 나타내는 proc 구조체의 포인터를 얻습니다.

각 CPU struct 는 proc 구조체를 가리키는 proc 필드를 가지고 있습니다. 어느 한 시점에 각 코어는 스케줄러 코드를 실행하고 있거나, 프로세스들 중 하나를 실행하고
있습니다. 프로세스를 실행 중이라면, 이 포인터는 유효하고 어떤 proc 구조체를 가리킵니다. CPU 가 스케줄러 코드를 실행 중이라면, 이 포인터는 null 입니다. 이 함수들은
꽤 직관적입니다.

다음으로 procdump 를 살펴보겠습니다. procdump 도 단순합니다. 기본적으로 디버깅 목적의 함수로, proc 배열을 훑으면서 정보를 출력합니다. 인자를 받지 않고, 반환
값도 없습니다.

무엇을 하느냐 하면, 말했듯이 전체 64개 proc 구조체 배열을 for 루프로 순회합니다. 각 struct 가 사용 중이 아니면, 즉 여기 state 가 UNUSED 라면 아무
것도 출력하지 않고 계속 진행해서 다음 반복으로 넘어갑니다. 그렇지 않은 경우에는, 여기 있는 배열을 사용해 state 값을 문자열로 변환합니다. 이 작은 배열은 UNUSED,
SLEEPING, RUNNABLE, RUNNING, ZOMBIE 같은 상수를 짧은 문자열로 매핑합니다. 여기서 그 문자열을 가져와 state 라고 부르고, 유효한 숫자인지 한 번
확인한 다음, 그 문자열을 사용합니다. 그리고 한 줄을 출력합니다. 이 한 줄에는 프로세스 id, 현재 상태, 그리고 name 이 포함됩니다. name 필드는 고정 길이 필드이고,
짧은 이름을 저장할 수 있습니다. 여기에서 그 name 을 출력합니다. 이게 procdump 의 전체 동작이고, 꽤 단순합니다.

이제 allocproc 함수로 들어가 보겠습니다. 이 함수가 무엇을 하는지 살펴보죠. 우선 인자를 받지 않습니다. 새로운 프로세스를 만들기 위해 새로운 proc 구조체가 필요할 때
allocproc 을 호출합니다.

그리고 `allocproc`는 프로세스 하나를 찾아서 초기화한 다음 그 포인터를 리턴할 겁니다. 프로세스 테이블에서 사용되지 않은 `proc`을 찾고, 찾으면 초기화하고, 락을
잡은 상태로 리턴합니다. 문제가 있으면 0을 리턴합니다.

이 함수가 하는 일을 개략적으로 보면 이렇습니다. 먼저 사용되지 않은 `proc` 구조체를 찾습니다. 그다음 그 프로세스를 위해 트랩프레임(trapframe)용 페이지를 할당하기
위해 `kalloc`을 호출합니다. 그리고 새 페이지 테이블을 만들면서, 모든 가상 주소 공간이 공유하는 트램펄린(trampoline) 페이지에 대한 매핑과, 방금 할당된
트랩프레임 페이지에 대한 매핑을 추가합니다. 그 다음 이 프로세스가 처음으로 스케줄될 때를 대비해서 컨텍스트(context)를 설정, 혹은 초기화합니다.

`proc` 구조체 안에 이 컨텍스트 영역이 있고, 이게 레지스터 저장 영역입니다. 그래서 여기에서 어느 정도 초기화를 해 줍니다. 그리고 이제 막 만든 주소 공간 — 즉 페이지
테이블을 만들었지만, 아직 그 안에 아무것도 넣지 않았기 때문에 코드나 데이터는 없습니다. `allocproc` 함수는 거기까지는 책임지지 않고, 코드와 데이터는 나중에
추가됩니다. 만약 중간에 어떤 문제가 생기면 이 함수는 지금까지 한 일을 전부 되돌려야 합니다. `kfree`를 호출해서 지금까지 할당한 페이지들을 모두 자유 페이지 풀로 되돌려
놓고, 0을 리턴합니다.

이제 코드를 보겠습니다. 여기서는 상태(state)가 `UNUSED`인 `proc` 구조체를 찾고 있습니다. 이 `for` 루프에서 전체 64개의 배열 요소를 전부 훑습니다. 각
요소마다 락을 얻고, 만약 `UNUSED`라면 찾은 것이므로 아래쪽 레이블로 점프하는 또 하나의 `goto`가 있습니다. 만약 사용 중이라면 락을 풀고 계속 찾습니다. 그리고
아무것도 찾지 못하면 0을 리턴합니다.

이제 무엇인가를 찾았다고 해 봅시다. 그러면 여기에서 프로세스 ID를 채웁니다. 각 프로세스는 새로운 식별자를 하나씩 받습니다. 이 변수가 오버플로되면 어떻게 될지에 대해서는 신경
쓰지 않습니다. xv6에서는 우리의 생애 동안 그런 일은 일어나지 않는다고 가정합니다. 그리고 상태를 `USED`로 설정합니다. 저 `USED` 상태가 여기 목록에는 안 나와
있네요. 어쨌든 이 상태가 `USED`가 되고, 호출한 쪽에서 나중에 이 프로세스를 `RUNNABLE` 상태로 만들어 줄 책임을 집니다.

그 다음 트랩프레임 페이지를 할당합니다. 여기서 `kalloc`을 호출하고, 무언가 잘못되면 락을 풀고 0을 리턴합니다. 이때 `freeproc` 함수도 호출하는데, 이건 다음에
설명하겠습니다. 기본적으로는 문제가 생길 때마다 호출되는 함수이고, 아래쪽에서도 호출되는 걸 볼 수 있습니다. 이 함수는 `proc` 구조체를 다시 `UNUSED` 상태로 만들고,
모든 필드를 0으로 초기화해서 재사용 가능하게 만드는 역할을 합니다.

이제 페이지 테이블을 만듭니다. 여기서 `proc_pagetable`을 호출하는데, 이것도 잠시 뒤에 다루겠습니다. 이 함수가 페이지 테이블을 만들고 몇 개의 매핑을 추가합니다.
이게 성공하면 그대로 진행하고, 실패하면 지금까지 한 일을 되돌리기 위해 `freeproc`을 호출하고, 락을 풀고, 위에서처럼 0을 리턴합니다.

`allocproc`은 두 곳에서 호출됩니다. 하나는 첫 번째 프로세스인 `init` 프로세스를 만들기 위한 `userinit`이고, 다른 하나는 `fork` 시스템 콜을 구현하는
`fork` 함수입니다. 어떤 경우든 프로세스가 생성된 다음에는 스케줄되어 실행될 것이므로, 그에 맞게 준비를 해야 합니다.

`proc` 구조체 안에는 레지스터 저장 영역이 있습니다. 이건 프로세스가 실행을 시작할 때 커널이 사용할 레지스터들입니다. 프로세스는 커널 모드에서 스케줄될 때 실행을
시작하므로, 나중에 복원될 레지스터들이고, 여기에는 `ra`와 `sp` 레지스터, 즉 리턴 주소와 스택 포인터도 포함됩니다.

이 프로세스는 처음 스케줄되는 것이지, 이미 돌고 있다가 다시 스케줄되는 것이 아닙니다. 따라서 처음 스케줄될 때 사용할 리턴 주소와 스택 포인터가 필요합니다. 그래서 컨텍스트를
설정하는데, 우선 `memset`으로 레지스터 저장 영역의 모든 레지스터를 0으로 초기화합니다. 그런 다음 `ra` 레지스터를 `forkret` 함수의 주소를 가리키도록
초기화합니다. 이 함수는 곧 살펴보겠습니다. 그리고 `sp` 레지스터는 스택 페이지를 가리키도록 초기화합니다.

각 프로세스는 가상 메모리 안에 스택용 페이지를 하나 가지고 있고, 예를 들어 프로세스 2는 이 가상 주소에 해당 페이지가 있습니다. 스택은 아래 방향으로 자라기 때문에, 스택
포인터는 이 페이지의 맨 위를 가리키도록 초기화해야 그 지점부터 아래로 자랄 수 있습니다. 그래서 스택 포인터를 이렇게 초기화해 두면, 이 프로세스가 스케줄되어 첫 번째 타임
