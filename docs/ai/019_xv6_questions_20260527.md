# xv6 질문 정리

이 문서는 xv6를 읽다가 이해되지 않은 부분을 짧게 누적한다.

형식:

```text
## N. 질문

답:

코드 위치:
```

## 1. 커널은 user program의 trap 처리와 scheduler 반복만 하나?

답:

거의 맞지만 표현을 나누는 편이 정확하다. xv6에서 boot 이후 각 CPU는 대체로 `user mode 실행`,
`process의 kernel stack에서 trap/syscall/interrupt 처리`, `scheduler context에서 runnable process 선택`
사이를 오간다. scheduler는 trap 자체를 기다리는 코드라기보다 runnable process를 찾고, 없으면 `wfi`로
interrupt를 기다린다.

코드 위치:

- `kernel/main.c:main()`
- `kernel/proc.c:scheduler()`
- `kernel/trap.c:usertrap()`, `kernel/trap.c:kerneltrap()`
- `kernel/trampoline.S:uservec`, `kernel/trampoline.S:userret`

## 2. `wfi`가 무엇인가?

답:

`wfi`는 RISC-V의 "wait for interrupt" 명령어다. 실행할 process가 없을 때 CPU가 바쁜 loop를 계속 도는
대신, interrupt가 올 때까지 쉬게 한다. xv6 scheduler는 runnable process를 못 찾으면 `wfi`를 실행하고,
timer/device interrupt가 오면 깨어나 다시 runnable process를 찾는다.

코드 위치:

- `kernel/proc.c:scheduler()`

## 3. 상태 전환 저장 패턴은 `trapframe`과 `context` 두 가지인가?

답:

현재 범위에서는 그렇게 봐도 된다. `trapframe`은 user/kernel 경계에서 user mode로 정확히 돌아가기 위한
저장소다. user general registers, saved user PC(`epc`), 다음 trap entry에 필요한 kernel page table/stack/
handler/hart id를 담는다. `context`는 scheduler와 process kernel thread 사이에서 kernel 실행 지점을
다시 시작하기 위한 저장소다. `ra`, `sp`, `s0-s11`만 담는다.

코드 위치:

- `kernel/proc.h:struct trapframe`, `kernel/proc.h:struct context`
- `kernel/trampoline.S:uservec`, `kernel/trampoline.S:userret`
- `kernel/swtch.S:swtch`

## 4. 왜 process kernel thread와 scheduler 사이의 `context`를 저장해야 하나?

답:

커널 코드가 여러 벌이라서가 아니라, 같은 커널 코드 위에 여러 kernel 실행 흐름과 stack이 있기 때문이다.
process가 `yield()`, `sleep()`, `kexit()` 등에서 scheduler로 넘어가면, 나중에 그 process의 kernel
call chain으로 돌아와야 한다. `context`는 그 재개 지점의 `ra`, `sp`, `s0-s11`을 저장한다. 각 CPU는
자기 scheduler context를 가지고, 각 process는 자기 kernel context와 kernel stack을 가진다.

코드 위치:

- `kernel/proc.h:struct cpu`, `kernel/proc.h:struct proc`, `kernel/proc.h:struct context`
- `kernel/proc.c:scheduler()`, `kernel/proc.c:sched()`
- `kernel/swtch.S:swtch`

## 5. scheduler로 넘어간다는 것은 실제로 무엇이 일어나는가?

답:

`sched()`가 `swtch(&p->context, &mycpu()->context)`를 호출한다. `swtch`는 현재 process kernel thread의
`ra`, `sp`, `s0-s11`을 `p->context`에 저장하고, CPU scheduler의 `context`에서 같은 register를 로드한 뒤
`ret`한다. 그래서 CPU는 process의 kernel stack/call chain이 아니라 scheduler의 stack/call chain에서
실행을 재개한다.

코드 위치:

- `kernel/proc.c:sched()`
- `kernel/proc.c:scheduler()`
- `kernel/swtch.S:swtch`

## 6. CPU scheduler가 별도로 존재하나? 8개 core 중 하나가 scheduler인가?

답:

전용 scheduler core가 있는 것이 아니다. xv6는 각 CPU(hart)가 자기 `scheduler()` loop를 실행한다.
`NCPU=8`은 최대 CPU 수이고, `cpus[NCPU]`에는 CPU별 scheduler context가 있다. 어떤 CPU든 process를
실행하다가 `sched()`로 자기 CPU의 scheduler context로 돌아간다.

코드 위치:

- `kernel/param.h:NCPU`
- `kernel/proc.h:struct cpu`, `kernel/proc.c:cpus`
- `kernel/main.c:main()`
- `kernel/proc.c:scheduler()`

## 7. CPU는 scheduler context와 kernel context를 번갈아 전환하나?

답:

대체로 맞지만 "그냥 kernel context"가 아니라 "특정 process의 kernel context"라고 보는 편이 정확하다.
각 CPU는 자기 scheduler context(`cpu.context`)와 선택된 process의 kernel context(`p->context`) 사이를
`swtch()`로 오간다. process context는 그 process의 kernel stack 위에서 `yield()`, `sleep()`,
`usertrap()` 이후 흐름 등을 재개하기 위한 것이다.

코드 위치:

- `kernel/proc.h:struct cpu`, `kernel/proc.h:struct proc`
- `kernel/proc.c:scheduler()`, `kernel/proc.c:sched()`
- `kernel/swtch.S:swtch`

## 8. 커널 바이너리는 누가 메모리에 올리고 PC를 맞추나?

답:

xv6/QEMU에서는 linker script가 `_entry`를 `0x80000000`에 배치하고, `qemu -kernel kernel/kernel`이
kernel ELF를 그 위치에 로드한 뒤 그 주소로 jump한다. 실제 머신에서는 보통 firmware/bootloader가 이 역할을
한다. RISC-V라면 ROM/firmware가 먼저 실행되고, OpenSBI 같은 machine-mode firmware나 bootloader가 kernel을
RAM에 올린 뒤 kernel entry로 제어를 넘기는 식이다.

코드 위치:

- `kernel/kernel.ld`
- `kernel/entry.S`
- `kernel/memlayout.h`
- `Makefile`
