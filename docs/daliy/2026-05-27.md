## 선행 개념

### `tramframe`과 `context`
- `trapframe`: user -> kernel 전환 시에 필요한 레지스터 값 저장 
- `context`: kernel <-> scheduler thread 전환 시에 필요한 레지스터 값 저장
  - hart(core)마다 있는 ctx는 scheduler, process 마다 있는 ctx는 kernel의 상태를 저장하고 있음.

### spinlock

락 건 소유자만 락을 해제할 수 있는데, 이 기준은 hart(core)이다. 

thread/process가 아님. switch 시에 필요하기 때문.

### 레지스터 종류

1. GPR, General-Purpose Registers
   - 일반 연산, 주소 계산, 함수 인자/반환값 등에 쓰는 범용 레지스터다.
   - 고정/특수 역할: `zero`, `ra`, `sp`, `gp`, `tp`(thread pointer, xv6에서는 hart id)
   - caller-saved: 호출한 쪽이 필요하면 call 전에 직접 저장해야 한다. 예: `ra`, `a0-a7`, `t0-t6`
   - callee-saved: 호출받은 쪽이 사용했다면 return 전에 원래 값으로 복구해야 한다. 예: `sp`, `s0-s11`

2. CSR, Control and Status Registers
   - CPU 제어 상태, trap, interrupt, page table 등을 관리하는 특수 레지스터다.
   - trap 관련: `stvec`, `sepc`, `scause`, `stval`, `sscratch`
   - privilege / interrupt 상태: `sstatus`, `sie`, `sip`
   - page table: `satp`
   - machine mode / boot 관련: `mstatus`, `mepc`, `mhartid`, `medeleg`, `mideleg`, `pmp*`

## 커널 로드 과정
1. 커널을 메모리 로드
   - (002번, 012번 문서 참고)
   - 커널 바이너리는 메모리 위치 등이 정해져있음. (링커 스크립트를 직접 작성해서 메모리 위치를 고정함)
   - QEMU의 경우는 해당 실행 파일을 로드하고 커널 코드의 위치로 pc를 조정함.
   - (실제 로드의 경우엔 firmware/bootloader가 해준다곤 함)
2. `main()` 실행 준비
   - (002번, 012번 문서 참고)
   - machine mode에서 hart(core)별 stack을 준비하고 그 외 여러 설정을 한다. 
     - 인터럽트 위임, 레지스터에 값 쓰기 등, machine mode에서 가능한 동작
   - 최종적으론 supervisor mode로 변환되며 `main()`으로 넘어간다. (커널은 supervisor mode로 동작한다.) 
3. `main()` 실행
   - (002번 문서 참고)
   - 멀티코어이므로 하나만 전체 초기화 작업을 수행함.
   - page table, tarpvec, meminint, 등의 대부분 초기화 작업을 수행.
   - 마지막으로 모든 hart는 `scheduler()`를 실행함.
4. 스케줄링 반복
   - `scheduler()` 내부에선 실행 가능한 process를 찾고 있으면 스위칭, 없으면 인터럽트가 생길때까지 대기를 수행한다.
   - 스위칭 시 process의 kernel stack과 현재(scheduler) stack을 전환이 발생한다. 
     - (해당 문장이 잘 이해 안가면 아래 스케쥴링 관련 설명 글 보기)

## 메모리 레이아웃

(자세한 구조는 010번 문서 참고)

- KVA와 PA는 Direct map이 되어있다. (128 MB만 사용)
  - `0x80000000` 부터 시작
- `Trampoline`은 KVA와 UVA가 동일한 주소를 본다.
  - 같은 VA를 PA의 `Trampoline` 매핑해둠. 
- 사용자 영역은 모두 커널의 kalloc page region 내에서 관리가 되며, `PGSIZE`(4KB) 단위로 관리한다.
- 커널 시작 주소 아래(`0x80000000`) 아래의 일부 PA는 QEMU virt machine에서 MMIO/firmware 용도로 배정되어 있다.
  - QMEU 기준인데, 실제의 경우는 어떤 식인지 모르겠음.
- VA에서 Direct map이외의 영역에 존재하는 것 처럼 보이지만, 실제로는 같은 physical page에 대한 별도 virtual mapping이 있다.
   - 처음 보면 헷갈리는 부분
   - 예: `Trampoline`, `Kstack 0..N번`

## trap과 syscall 처리 흐름

(자세한 구조는 013번 문서 참고)

큰 흐름만 정리, 이 외에도 여러 일을 함.

- hardware: trap 발생 시 supervisor mode로 변경하고 `stvec`의 PC로 이동
- `trampoline.S > .uservec`: user register들을 현재 process의 `trapframe`에 저장하고, `trapframe`에 담긴 값을 보고 kernel로 변경
- `trap.c > usertrap()`: 적절하게 인터럽트 처리 (여기선 중요한 주제 아님)
- `trap.c > prepare_return()`: 다음 trap 진입에 필요한 커널 register를 다시 `trapframe`에 저장해둠
- `trampoline.S > .userret`: `trapframe`에 저장된 user register를 로드

## context switch와 scheduling

(자세한 구조는 015번 문서 참고)

- `scheduler()`는 hart(core)마다 실행된다.
  - 각 hart는 자기 scheduler context를 가지고 있다. (`cpu.context`)
- process마다 kernel context를 가지고 있다. (`p->context`)
- 각 context는 scheduler/kernel(process)가 실행되던 지점을 다시 이어가기 위한 값이다.
  - `ra`, `sp`, `s0-s11`을 저장/로드
- switch 시, CPU가 바뀌지 않고, 같은 CPU에서 context 값에 따라 실행 흐름만 변경된다.
- `p->lock`은 switch 중 process state와 context를 보호한다.
  - 동일한 CPU에서 실행중이므로 scheduler/kernel(process) 가 락을 걸고 다른 쪽에서 풀 수 있다.

## sleep/wakeup

(자세한 구조는 016번 문서 참고)

- 커널에서 쓰는 process를 대기 시킬 때 쓰는 함수이다.
  - `sleep(chan, lock)`은 특정 조건이 만족될 때까지 현재 process를 재우는 함수다.
  - `wakeup(chan)`은 같은 `chan`에서 자고 있는 process들을 `RUNNABLE`로 바꾼다.

lost wakeup을 막기 위해서, 사용 시에는 다음과 같은 패턴을 사용한다. (condition wait 패턴)

```c++
acquire(condition_lock)
while condition is false:
    sleep(chan, condition_lock)
release(condition_lock)
```
