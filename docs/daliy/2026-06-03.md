# 26. Traps in kernel mode

AI 정리: [docs/ai/027_xv6_script_26_traps_in_kernel_mode_20260603.md](/docs/ai/027_xv6_script_26_traps_in_kernel_mode_20260603.md)

하드웨어(디바이스/타임) 인터럽트의 경우 즉각적인 처리를 필요로 한다. 그래서 커널 모드에서도 하드웨어 인터럽트는 받을 수 있어야 한다. (나머지는 panic 처리)

시스템 콜 처리 중에는 커널 코드가 오래 실행될 수 있어서 이 때는 복귀 가능한 상태를 저장해두고 인터럽트를 킨다.

커널 모드의 트랩 처리 시에는 `trapframe` 전환이 필요 없기 때문에 다른 exception table을 보게 한다.    
`stvec`을 `kernelvec`로 바꾸고 kernel의 stack에 register 정보를 저장한다.

Linux는 커널 모드에서 발생한 page fault 같은 일반 예외까지도 일부 처리할 수 있다. 다만 의도하지 않은 예외들은 패닉으로 이어지는듯 함.

# 27. PLIC: Platform-Level Interrupt Controller

AI 정리: [docs/ai/028_xv6_script_27_plic_platform_level_interrupt_controller_20260603.md](/docs/ai/028_xv6_script_27_plic_platform_level_interrupt_controller_20260603.md)

강의에선 되게 구체적인데, 그렇게까지 관심있는 주제는 아니라 AI 문서도 단순하게 정리.

Interrupt controller = 여러 장치 interrupt를 여러 CPU/core에 라우팅하고 관리하는 하드웨어

왜 필요한가?
- hart는 다음 명령어 실행 전에 trap을 처리 가능하면 trap 처리를 시도한다. (하드웨어 구현이 그렇게 되어있음.)
- 여러 장치와 여러 hart가 존재하므로, 우선순위에 따라 IRQ(Interrupt Request)를 적절한 hart에 분배하는 등의 작업을 해줘야 함.
  - 특정 hart에는 어떤 기기의 IRQ를 처리할 수 없다거나 하는 규칙이 있을 수도 있음.

PLIC: RISC-V에서 제공하는 Interrupt controller 중 하나

PLIC도 장치긴 하니까 MMIO로 통신함. 

device interrupt 발생 시에는 trap 처리 중 `devintr()`로 분기하여 PLIC와 통신해서 특정 IRQ를 처리할 hart 정하고 작업을 수행한다.

software/timer interrupt는 PLIC와 통신하지 않는다. 이것들은 외부 장치와 통신하는게 아니라서. (time는 hart-local timer에서 발생하는 인터럽트임)

# 29. Disk Log File

AI 정리: [docs/ai/030_xv6_script_29_disk_log_file_20260603.md](/docs/ai/030_xv6_script_29_disk_log_file_20260603.md)

범용적으론 crash consistency라고 표현하는 듯 한다.

이런 트랜잭션이나 journaling은 보통 file system이 자기 on-disk 구조를 안전하게 갱신하기 위해 구현한다고 함.

왜 필요하나면, 파일 시스템은 정해진 형식이 있는데, 이 단위가 원자적으로 수행되어야 함.
그렇지 않으면, 작업 도중에 crash(비정상적 종료)로 인해 변경이 일부만 반영될 수 있고, 파일 시스템 구조가 잘못된 상태가 될 수 있다.

xv6는 별도 디스크 영역에 트랜잭션으로 묶인 작업을 별도 Disk에 저장해두고, 커밋 시에 연관된 모든 변경을 한번에 쓰는 식으로 사용한다.
