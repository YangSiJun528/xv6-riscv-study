## 21. Process creation

그냥 프로세스 생성 과정을 소개.

프로세스 생성/제거 시 `kernel stack, trapframe, user page table, user memory, kernel context` 를 관리한다.

fork 시에 첫 실행이면 특정 처리를 하는 식으로 도는 초기화 설정들이 있음, sleep lock이 필요해서 main에서 처리를 못하기 때문.

강의와 현재 코드의 차이가 있는데, 현재 코드가 훨씬 깔끔한거 같긴 함. 굳이 별도 과정 없이 `exec`으로 합쳐버린거니까.

## 22. Anatomy of a system call

사실 상 6번, 13~15번 에서 설명한 내용을 합친 것.

시스템 콜 호출 과정을 `sbrk()` 시스템 콜을 예시로 구체적으로 다루지만, 이미 알고있던 내용들이라 구체적인 정리는 필요없어보임.

- 시스템 콜 함수는 스크립트를 통해 어셈블리로 생성되고 trap을 호출한다.
- 하드웨어는 최소한의 CSR 정보만 저장하고, `uservec`로 이동한다.
- trampoline은 user <-> kernel 상태를 전환 시 이전 상태를 저장한다.
- 커널은 trap 처리 중, syscall 호출임을 인식하고 적절하게 처리된다. 
- 다시 trampoline을 통해 상태를 전환하고 시스템 콜 함수 다음 줄부터 실행된다.

## 24. exit/wait/kill syscalls

Pintos 때는 부모/자식 상태 전달을 ref cnt 기반의 구조체로 처리했는데, 

xv6의 구현은 실제 리눅스(UNIX)의 방식에 더 가깝다. https://labex.io/lesson/process-termination

좀비 프로세스는 부모가 `wait()`으로 종료 상태를 확인해야 리소스가 해제되고, 고아 프로세스가 되면 `init`이 re-parents(adoption)한다.   
(아마 종료 상태를 확인할 수 있어야 하기 때문인듯?, `user/init.c`를 보면 반복해서 `wait` 하는걸 볼 수 있다.)

그리고 `sleep()`에 왜 인자 이름이 channel이나 했는데, `wait()`에서 `sleep()`을 쓸 때는 proc 구조체의 주소를 써서 처리하고 있었음. 
그러면 깨우고 잠들게 하는 로직을 재사용 가능하니까.

`wait_lock`은 parent/child 관계를 보호하는 전역 락이다.      
`fork()`/`wait()`/`exit()`/`reparent()` 에서도 쓰는데, 이것들 다 부모/자식 관계를 수정하거나 읽는 함수들임.   
그래서 이 경우에는 한 실행 단위?만 접근 가능하게 보호해야만 함.
